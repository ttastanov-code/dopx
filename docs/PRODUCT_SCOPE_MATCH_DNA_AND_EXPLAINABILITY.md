# Скоуп: DOPX Match DNA, "Почему он в сборной?", Индекс настроения клуба

Дата: 2026-09-05
Статус: Скоуп (без реализации) — см. `docs/CODEX_AUDIT_RESPONSE_2026-09-04.md`,
корзина В: "согласен, сильные идеи, но осознанно после трастовых фиксов
(P0 + анти-шум), иначе это красивая витрина поверх данных, которым нельзя
доверять". Трастовые фиксы (`docs/adr/0001`, `docs/adr/0005`) уже сделаны
— это разблокирует скоупинг, НЕ разрешение сразу строить. Каждая фича
ниже требует отдельного решения "делаем/не делаем" после этого документа.

Три идеи объединяет одно: все три — "витрина" поверх уже существующих
рейтингов, ни одна не требует новых источников данных о самом матче
(KFF), только новую логику НАД тем, что уже посчитано аггрегатами.

---

## 1. "Почему он в сборной?" (объяснимость Best XI / Тура)

### Что уже есть

Выбор слота — Bayesian-shrinkage ранжирование `PlayerMatchAggregate.performance_score`
(`season_squad/services.py::_bayes_score`/`_rank_pool`,
`round_squad/services.py::_round_bayes_score`/`_rank_round_pool`).
Объяснение УЖЕ генерируется — `_build_explanation`
(`season_squad/services.py`) и `_build_round_explanation`
(`round_squad/services.py`) — но это ОДНО предложение уровня "рейтинг X,
уверенность зависит от размера выборки, место в рейтинге не изменилось/
поднялось" (см. `docs/adr/0026`). Это объясняет ЧИСЛО, а не то, ЗА ЧТО
именно игрок получил высокие оценки — нет разбивки по конкретным
событиям/критериям, которые реально подняли рейтинг.

### Что нужно добавить

`PlayerMatchAggregate` уже хранит покомпонентные средние
(`avg_contribution`/`avg_risk`/`avg_potential`) — этого достаточно для
объяснения БЕЗ новых полей на уровне одного матча. Реального пробела два:

1. **Агрегация "почему" по НЕСКОЛЬКИМ матчам** — Best XI сезона/тура
   считается по среднему из нескольких `PlayerMatchAggregate`, а не по
   одному матчу; объяснение сейчас не разбивает "средний вклад" на
   конкретные матчи/события ("гол в дерби 24.08" вместо просто "8.4
   средний контрибьюшн").
2. **Связка рейтинга с реальными событиями матча** (`MatchEvent`) —
   сейчас `_build_explanation` не читает `MatchEvent` вообще, только
   агрегаты. "Ключевой момент: гол на 78-й минуте против лидера
   чемпионата" — это то, что реально продаёт объяснение пользователю
   (сравнимо с эвристикой `EvaluatePlayersView._compute_key_player_ids`
   из `docs/adr/0006`, которая уже связывает `MatchEvent` с "заметностью"
   игрока — тот же источник данных, новое применение).

### MVP-предложение

Не новая модель — функция `_build_rich_explanation(player, slot_context)`,
дополняющая (не заменяющая) текущий `_build_explanation`:
- Топ-2 матча по `performance_score` из тех, что вошли в усреднение,
  с датой и соперником.
- Если у игрока в этих матчах есть заметное `MatchEvent`
  (гол/ассист/red_card — тот же список, что в `_compute_key_player_ids`)
  — одна строка "отличился: гол (78'), жёлтая карточка (12')".
- Показ — расширение существующего тултипа `_confidence_badge`-типа
  партиала на карточке слота (`_role_card.html`/`_player_card`-эквивалент
  в season_squad/round_squad), не новая страница.

### Оценка сложности

Низкая-средняя. Все данные уже в БД, требуется только Python-функция
агрегации + один партиал. Не требует Celery/фоновых задач — считается на
чтении, как и текущий `_build_explanation`.

### Риск

Отбор "заметных" событий (голы/карточки) как прокси важности — тот же
осознанный компромисс, что уже описан в `docs/adr/0006`
("самый дешёвый доступный прокси заметности"). Не является объективной
мерой вклада (защитник, отработавший идеально без единого события,
объяснения не получит) — подавать как "что бросается в глаза", не как
"научное обоснование места в составе".

## 2. DOPX Match DNA

### Что уже есть

`MatchAggregate` — `avg_entertainment`/`avg_tension`/`avg_fairness`/
`turning_point_ratio`/`drama_index` (уже вычисляемая метрика
"зрелищность × напряжение"). `MatchEvent` — полная лента событий с
минутами. `build_match_share_card` (`core/services/share_cards.py:538`)
— уже существующая, но МИНИМАЛЬНАЯ карточка (счёт + топ-игрок), не
"ДНК"-нарратив.

### Что нужно добавить

"ДНК матча" — это не новые данные, а НОВАЯ КОМПОЗИЦИЯ уже посчитанного:
`drama_index` (уже есть) + топ-3 momentum-точки матча (по `MatchEvent`,
сгруппированным по времени — "первый тайм спокойный, три гола после
75-й минуты") + расхождение мнений болельщиков разных лагерей (уже
есть `own_fans_avg`/`rival_fans_avg`/`neutral_avg` на `TeamMatchAggregate`,
можно показать как "болельщики Кайрата и Актобе разошлись во мнениях о
судействе на 12.3 балла" — готовый, уже подсчитанный сигнал, просто
никогда не выводился пользователю как отдельная история).

Новое, чего в БД нет: ничего структурного — только текстовый "рендерer",
переводящий уже посчитанные числа в 4-6 строк нарратива + новая карточка
для шаринга (`build_match_dna_share_card`, по аналогии с существующими
пятью функциями `share_cards.py`).

### MVP-предложение

Фаза 1 (без Celery, без новых моделей): секция на `matches/detail.html`
под `_match_events.html` — "ДНК матча": `drama_index` как визуальный
градус (уже есть, просто не показан на странице матча напрямую — сейчас
виден только через агрегат), 1-2 momentum-точки (наибольшее число
событий за 15-минутный интервал), одно предложение про расхождение
лагерей (если сегментов ≥ 2, тот же гейт что у `bias_segment_text`).

Фаза 2 (после фазы 1, если приживётся): шаринговая карточка через
`core/services/share_cards.py`, тот же принцип, что у `build_badge_share_card`
— вызывается по кнопке "Поделиться" на странице матча, не автоматически.

### Оценка сложности

Средняя. Текст/карточка — как фаза 1 у "Почему он в сборной" (чтение,
без фоновых задач). Momentum-детектор по времени — новая, но небольшая
функция (группировка `MatchEvent` по 15-минутным окнам, уже есть
прецедент группировки по `event_type` в `_compute_key_player_ids`).

### Риск / монетизационный угол

Match DNA — самая сильная кандидатка на виральный шаринг (карточка
конкретного матча, интересна болельщикам ОБЕИХ команд, не только
подписчикам DOPX) — прямое продолжение уже работающей механики
share-карточек достижений. Не начинать с шаринговой карточки (фаза 2) до
проверки, что сама секция на странице матча (фаза 1) вообще востребована
— цена ошибки на карточке (дизайн, шрифты, легибилити — см.
`docs/adr/0011`) выше, чем на текстовой секции.

## 3. Индекс настроения клуба (Club Mood Index)

### Что уже есть

Ничего — это единственная из трёх идей, требующая НОВОГО агрегата.
`TeamSeasonStats` (`teams/models.py`) — только W/D/L/очки/место, из
результатов матчей, не из оценок болельщиков. `TeamMatchAggregate` —
только single-match срез, нет временного ряда.

### Что нужно добавить (и это существенно больше двух предыдущих)

1. **Новая модель** `TeamMoodSnapshot` (или расширение `TeamSeasonStats`)
   — периодический (еженедельный/потуровый) срез: средний
   `performance_score`/`avg_*` команды за скользящее окно N последних
   матчей, направление тренда (рост/падение), возможно доля
   `own_fans_avg` vs `rival_fans_avg` как прокси "внутреннего" недовольства
   болельщиков своей же командой (низкие оценки от СВОИХ фанатов — более
   сильный сигнал "настроения", чем усреднённая оценка со всеми чужими).
2. **Celery periodic task**, аналогичный `recalculate_season_standings`
   (`aggregates/tasks.py:718`) — считает срез после каждого завершённого
   матча команды или по расписанию (потурово).
3. **UI** — страница команды, новый блок с трендом (спарклайн/график
   последних N срезов) — нужна визуализация временного ряда, которой в
   проекте пока нигде нет (все существующие графики — статичные
   одноразовые распределения, не time series).

### MVP-предложение

НЕ строить сразу полноценный индекс. Сначала — минимальный "трендовый
бейдж" (↑/↓/→ за последние 5 матчей команды по среднему
`TeamMatchAggregate.performance_score`), без отдельной модели: считается
на лету при рендере страницы команды из уже существующих
`TeamMatchAggregate` (`ORDER BY match__start_time DESC LIMIT 5`),
кэшируется на разумное время. Полноценный time-series индекс с историей
— только если этот минимальный сигнал подтвердит интерес пользователей
(кликают/спрашивают "почему тренд такой").

### Оценка сложности

Средняя (MVP-версия без модели) → высокая (полноценная версия с историей,
Celery, визуализацией). Единственная из трёх идей, для которой
"построить сразу правильно, без промежуточных версий" (общий принцип
проекта) означает СНАЧАЛА проверить продуктовую гипотезу дешёвым
способом, а не сразу проектировать финальную модель данных — здесь
психологическая метрика ("настроение") достаточно спекулятивна, чтобы
рискнуть спроектировать не ту схему хранения при первом заходе.

### Риск

Самая чувствительная из трёх идей репутационно — "индекс настроения
клуба" звучит как объективная метрика, но фактически производная от той
же самой болельщицкой предвзятости, для которой в проекте уже есть
целый анти-фрод контур (`aggregates/tasks.py`, `docs/adr/0009`). Если
индекс будет заметно "радовать" фанатов топ-клубов и "расстраивать"
аутсайдеров вне зависимости от реальной игры команды — это ударит по
доверию к платформе сильнее, чем отсутствие фичи. Публиковать только
после того, как MVP-версия прогонится "в фоне" (посчитана, но не
показана публично) минимум один полный круг чемпионата — сверить с
объективными результатами (позиция в таблице, форма по очкам) на
предмет систематических перекосов.

## Рекомендованный порядок (если решено делать)

1. "Почему он в сборной?" — минимальный риск, максимальное переиспользование
   существующих данных, усиливает уже работающую фичу (Best XI), а не
   создаёт новую поверхность.
2. Match DNA, фаза 1 (текстовая секция) — следующий по готовности данных,
   прямая связь с трастовыми фиксами этой сессии (drama_index,
   bias-сегменты уже посчитаны честно).
3. Match DNA, фаза 2 (шаринговая карточка) — только после проверки фазы 1.
4. Индекс настроения клуба — последним и только MVP-версией (тренд-бейдж
   без новой модели), с обязательным "теневым" прогоном перед публичным
   показом.

Ни один из четырёх пунктов не запланирован к реализации в рамках этой
сессии — это чисто оценочный документ по явному запросу "scope first".
