# 0045 — Статистика матча в быстрой оценке игроков + анти-фрод на уровне игрока

Дата: 2026-09-08
Статус: Accepted

## Контекст

Пользователь спросил, можно ли использовать статистику матча (теперь
доступна от Sportmonks — `MatchPlayerStatistics`, фаза 3/5 миграции), в
комбинации с событиями матча, для (1) рекомендаций при быстрой оценке
игроков и (2) борьбы с накруткой/неадекватной оценкой. Уточняющий вопрос
пользователю показал три варианта; выбраны: умный выбор "ключевых игроков",
показ статистики на карточке (без автоматики) и анти-фрод на уровне игрока.
Явно НЕ выбраны пресеты значений слайдеров по статистике — см. обоснование
ниже.

## Решение

### 1. Умный выбор "ключевых игроков" (quick-режим оценки)

`evaluations/views.py::EvaluatePlayersView._compute_key_player_ids` раньше
подсвечивал только участников заметных событий (гол/карточка/автогол).
Добавлен `_stats_notable_player_ids` — второй, независимый источник
"заметности" по `MatchPlayerStatistics`: удары в створ ≥2, ИЛИ удары ≥4,
ИЛИ сейвы ≥3 (пороги раздельные — вратарь без единого удара по чужим
воротам не должен теряться из-за порога, рассчитанного на полевого игрока).
Объединяется с событийным набором через `|=`, остальная логика (добивание
до `KEY_PLAYERS_PER_SIDE` стартовым составом) не изменилась.

### 2. Статистика на карточке — только информация, без автозаполнения

На карточке игрока (`templates/evaluations/_player_card.html`) под именем
показываются готовые строки вида "3 удара (1 в створ)" / "4 сейва" — из
`evaluations/views.py::_player_stats_badges`. Сознательно НЕ предзаполняет
ползунки "Вклад"/"Риск"/"Потенциал" — см. обсуждение с пользователем: "Риск"
и "Потенциал" суть субъективные суждения, статистика ОДНОГО матча не может
их осмысленно "порекомендовать", а автозаполнение "Вклада" по формуле
рисковало бы просто подменить мнение пользователя числом. Статистика влияет
ТОЛЬКО на то, чья карточка раскрыта по умолчанию (пункт 1 выше) — сам выбор
баллов остаётся полностью за человеком.

Важная деталь реализации: русское склонение (1/2-4/5+, "сейв/сейва/сейвов")
посчитано в Python (`_pluralize_ru`, обобщение уже существовавшего
`matches/services.py::_pluralize_goals`) — НЕ через встроенный Django-фильтр
`|pluralize`. У `|pluralize` максимум ДВЕ формы (singular/plural suffix); при
трёх формах через запятую он молча возвращает пустую строку (см.
`django/template/defaultfilters.py`) — первая версия этого шаблона содержала
именно эту ошибку, поймано и исправлено в этой же сессии до релиза.

### 3. Анти-фрод на уровне игрока — `PlayerRatingCorrection`

Прямой аналог уже существующей команднoй системы (`TeamRatingCorrection` +
`detect_rating_stats_divergence_task`, ADR-0009, 2026-08-24) — та же
механика: автоматическая, ограниченная (`PLAYER_STATS_DIVERGENCE_MAX_
CORRECTION = 0.4`), самозатухающая (`*0.5` за прогон, если паттерн не
подтверждён) поправка к `performance_score`, применяется ТОЛЬКО на
пересчёте будущих агрегатов, никогда не переписывает уже показанную
историю. Флаг для прозрачности (`SuspiciousActivityFlag`, новый источник
`player_stats_divergence`), модератор может отклонить через `mark_dismissed`
(та же защита от "тихой перезаписи решения" через `suppressed_until` +
30-дневный cooldown, что и у команды).

**Ключевое архитектурное отличие от команды**: у `TeamRatingCorrection`
объективный сигнал — "доля доминирования" (0..1, сравнение с СОПЕРНИКОМ в
том же матче: удары в створ + угловые). У игрока такого естественного
"соперника для сравнения" нет — вратарь и нападающий структурно дают разные
абсолютные цифры (сейвы vs удары), сравнивать их напрямую бессмысленно.
Поэтому `_player_objective_score` (композитный индекс из голов/ассистов/
карточек/ударов/сейвов/фолов/незабитых пенальти, веса — `PLAYER_OBJECTIVE_
*_WEIGHT`) сравнивается НЕ с чужим профилем, а с СОБСТВЕННОЙ историей того
же игрока (self-relative z-score) — это само по себе корректно учитывает
амплуа без отдельной калибровки по позиции.

Композитный индекс — намеренно грубая, прозрачная формула (гол/ассист самые
тяжёлые веса, удары в створ/сейвы умеренный плюс, карточки/фолы/незабитый
пенальти умеренный минус), не ML-модель — соответствует духу остальных
антифрод-сигналов проекта (MAD/z-score, а не чёрный ящик).

## Побочные находки при реализации (в рамках "перепроверь весь проект")

- `SuspiciousActivityFlag.SOURCE_CHOICES` — запись `stats_divergence` была
  подписана "...с объективной статистикой KFF"; источник статистики сменился
  на Sportmonks ещё в фазе 5. Поправлена формулировка (миграция
  `users/0020`), заодно добавлен новый источник `player_stats_divergence`.
- Аналогичная стилистическая правка в докстринге модели (`users/models.py`)
  и в комментарии `CELERY_BEAT_SCHEDULE` (`dopx/settings.py`).

## Альтернативы и почему не они

- **Пресеты значений слайдеров по статистике** (как у тренера/судьи —
  Слабо/Нормально/Сильно) — рассмотрено и отклонено пользователем: работало
  бы для объективно измеримого "Вклада", но "Риск"/"Потенциал" — категории
  человеческого суждения (склонность к ошибкам, потолок роста), статистика
  одного матча их не описывает; смешивать "объективный" пресет с заведомо
  субъективными критериями было бы вводящим в заблуждение.
- **Единая объективная шкала 1-10 вместо self-relative z-score** — отклонено:
  потребовало бы отдельной калибровки "что такое хороший объективный
  индекс" для каждого амплуа (вратарь/защитник/полузащитник/нападающий) —
  на старте сезона, без накопленной лиговой статистики по позициям, такая
  калибровка была бы произвольной. Self-relative сравнение (игрок против
  самого себя) не требует этой калибровки вообще.

## Верификация

`python3 -m py_compile` на всех изменённых/созданных файлах — чисто.
`CELERY_BEAT_SCHEDULE` дополнительно провалидирован через `exec()` с
заглушкой `crontab()` — 26 записей, новая `detect-player-rating-stats-
divergence` на месте. Баланс Django-тегов в изменённом шаблоне
(`_player_card.html`) проверен построчным regex-подсчётом `{% if/for %}` /
`{% endif/endfor %}`. Живой прогон (реальные `PlayerEvaluation`/
`MatchPlayerStatistics` на настоящем сезоне) недоступен в песочнице агента —
как и во всех предыдущих фазах миграции, финальная проверка на живых данных
остаётся за пользователем.
