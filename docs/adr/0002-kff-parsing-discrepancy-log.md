# 0002 — Журнал расхождений импорта KFF (ParserDiscrepancy)

Дата: 2026-09-04
Статус: Accepted

## Контекст

Внешний аудит (см. `docs/CODEX_AUDIT_RESPONSE_2026-09-04.md`) указал на
риск бесплатного парсинга KFF как источника данных: если внешний сайт
задним числом поправит уже опубликованный результат матча, у DOPX не было
способа это заметить — обновление прошло бы тихо, наравне с обычным
прогрессом матча.

Проверка по коду показала, что существующий мониторинг
(`ParserSyncRun` — счётчики запуска, `error_samples`, алерты на высокий
процент ошибок; `_detect_rescheduled_outlier` — перенос дат; авто-снятие
`is_active` у игроков, пропавших из состава на kffleague.kz, с email-алертом
и ручной отменой) закрывает соседние риски, но НЕ этот конкретный: правку
счёта/статуса уже завершённого матча. Единственное место, где такая правка
физически может прийти — `parsers/kff/importers.py::import_match_core`,
через `Match.objects.update_or_create(...)`, когда `existing.status ==
"finished"` до этого импорта (`was_finished_before`, уже вычислялся в коде
для другой цели — уведомлений подписчикам).

## Решение

Модель `ParserDiscrepancy` (`parsers/models.py`) — одна запись на каждое
изменившееся поле (`status`/`home_score`/`away_score`) у матча, который уже
был `finished`. Пишется функцией `_record_finished_match_discrepancies` в
`parsers/kff/importers.py`, вызываемой из `import_match_core` до
`update_or_create` (пока `existing` ещё хранит старые значения).

Обычный прогресс матча под это не подпадает: `update_match_statuses`
(периодическая синхронизация статусов) явно исключает `finished` из
`active_matches`, и первый переход в `finished` через `import_match_core`
не считается расхождением (`was_finished_before` в этот момент ещё `False`).

Staff разбирает записи в Django admin (`ParserDiscrepancyAdmin`) — руками
отмечает `reviewed`, без автоматического отката значений: решение всегда
принимает человек. Счётчик неразобранных — на дашборде "Здоровье данных"
(`dashboard/services.py::data_health_summary`), рядом с уже существующими
карточками ошибок синка.

## Альтернативы и почему не они

- **Просто добавить это в `ParserSyncRun.error_samples`** — отклонено:
  `error_samples` — это исключения при запросе к API (сетевые сбои,
  парсинг ответа), семантически другое событие. Смешивание усложнило бы и
  код, и последующий анализ ("сколько у нас РЕАЛЬНЫХ ошибок API" перестало
  бы быть точным числом).
- **Автоматический откат к старому значению** — отклонено: у DOPX нет
  способа знать, какое из двух значений (наше старое или новое от KFF)
  правильное — это ровно то, что должен решить человек, посмотрев в
  официальный протокол федерации.
- **Ждать перехода на Stratorium и не чинить это сейчас** — отклонено:
  переход платный и не завтра, а до него степень доверия к бесплатному
  источнику ниже, то есть мониторинг нужнее именно сейчас, а не после.

## Последствия

- Новая модель = новая миграция (`parsers/migrations/0002_parserdiscrepancy.py`,
  написана вручную — makemigrations недоступен в песочнице разработки без
  подключённой БД, как и остальные миграции этого проекта).
- Тесты: `parsers/tests.py::FinishedMatchDiscrepancyTests` — три сценария
  (реальная правка счёта → запись создаётся; повторный импорт тех же
  значений → без шума; обычный переход в `finished` → без шума).
