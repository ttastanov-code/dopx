# 0038 — Временное разрешение KFF: единая защита от блокировок на весь парсер

Дата: 2026-09-07
Статус: Accepted

## Контекст

Прямой запрос: "кфф дали добро на парсинг их данных временно. поэтому
сделай парсер стабильным и чтобы блокировок не было никаких". Уточнил у
пользователя формат разрешения — устное, без оговорённых условий (нет
лимита запросов, нет требования к User-Agent, нет whitelisted IP, нет
API-ключа).

Устное разрешение — факт про людей на стороне KFF, а не про Cloudflare Bot
Management, который продолжает банить по TLS-отпечатку независимо от
разговоров, пока (и если) кто-то у KFF явно не занесёт нас в whitelist на
уровне инфраструктуры. Поэтому убирать TLS-маскировку (curl_cffi) или
circuit breaker было бы неверным выводом из разрешения — технический риск
блокировки Cloudflare не изменился ни на йоту.

При этом аудит существующего кода вскрыл ДВЕ реальные проблемы, обе прямо
по теме "стабильно, без блокировок":

1. **`parsers/kff/photo_scraper.py` — вообще без защиты.** Это ОТДЕЛЬНЫЙ
   от JSON API (`parsers/kff/client.py`) путь на ТОТ ЖЕ хост kffleague.kz
   (HTML-скрапинг составов команд, `sync_kff_player_meta`, раз в 3 дня по
   расписанию) — обычный `requests.Session()`, без curl_cffi, без circuit
   breaker, без общего состояния с JSON API вообще. Если Cloudflare банит
   нас через ЭТОТ путь, JSON API ничего об этом не узнаёт и продолжает
   слать запросы как ни в чём не бывало — и наоборот. Раньше "защита от
   банов" на самом деле покрывала только часть парсера.

2. **Circuit breaker JSON API считал неудачей ЛЮБОЙ код ответа, не только
   признаки блокировки.** `update_match_statuses` перебирает десятки
   матчей за один прогон; обычный 404 у ОДНОГО матча (например, статистика
   ещё не опубликована — штатная ситуация) засчитывался туда же, куда и
   403 (реальный бан). Несколько таких "нормальных" 404 подряд у разных
   матчей МОГЛИ накопиться до порога и ложно свалить весь прогон в
   15-минутный cooldown — самим кодом созданная "блокировка" на пустом
   месте, без единого реального бана от KFF.

## Решение

### 0. Правка по ходу (тот же день) — убран идентифицирующий заголовок

Первая версия этого ADR вводила заголовок `X-DOPX-Client` (честная
идентификация поверх обычной браузерной маскировки). Пользователь на это
резко возразил: разрешение KFF — повод УСИЛИТЬ защиту от банов, а не
рисковать "засветиться" перед Cloudflare раньше, чем KFF сама явно занесёт
нас в whitelist на своей стороне. Заголовок и функция
`kff_identity_headers()` убраны целиком (`client.py`, `photo_scraper.py`,
`PARSER_SETTINGS['CLIENT_IDENTIFIER']` в `settings.py`) — с точки зрения
Cloudflare клиент снова полностью неотличим от обычного браузерного
трафика, как и до всего этого разговора. Пункты 2 и 3 ниже (общий circuit
breaker на весь KFF-трафик и различение реальной блокировки от обычной
ошибки ответа) — это тот самый "хол-фикс", который пользователь подтвердил
и попросил оставить, они не менялись.

### 2. Единый circuit breaker на ВЕСЬ KFF-трафик

Логика circuit breaker вынесена из методов `KFFClient` в module-level
функции `check_kff_circuit_breaker()` / `register_kff_success()` /
`register_kff_failure()` (`parsers/kff/client.py`) — общее состояние в
Redis, которое теперь использует и `photo_scraper.py`. `_session()` там
получила curl_cffi (тот же `impersonate="chrome"`, что у JSON API-клиента,
с тихим fallback на requests, если пакет недоступен) — БЕЗ каких-либо
дополнительных заголовков сверх обычных браузерных (см. пункт 0 выше).
`_fetch_html()`/`download_photo_bytes()` проверяют cooldown до запроса и
регистрируют результат после — блокировка, замеченная одним путём, теперь
немедленно останавливает оба.

`parsers/tasks.py::sync_kff_player_meta` ловит `KFFAPICircuitBreakerOpen`
отдельно от общего `Exception` вокруг `match_teams()` (не ретраит — ретрай
всё равно попал бы внутрь того же 15-минутного cooldown) и вокруг цикла по
командам (`break`, не `continue` — тот же паттерн, что уже применён
2026-09-07 к `sync_recent_matches` для JSON API, см. её докстринг про
"каждый понедельник").

### 3. Различение реальной блокировки от обычной ошибки ответа

`KFFClient.KFF_BLOCK_SIGNAL_STATUS_CODES = {403, 429, 503}` — единственные
коды, которые теперь считаются признаком блокировки/рейт-лимита. Любой
другой код ответа (404/400/401/500 и т.п.) означает "сервер нам ОТВЕТИЛ
как обычному клиенту" — доказательство, что блокировки прямо сейчас нет —
и явно СБРАСЫВАЕТ счётчик неудач, как и настоящий успех. Общий набор
(`KFFClient.KFF_BLOCK_SIGNAL_STATUS_CODES`), не копия в photo_scraper.py.

На 429 дополнительно уважается `Retry-After` из ответа (капается 30
секундами, чтобы не подвесить весь прогон на одном запросе) вместо
собственного фиксированного бэкоффа — корректное HTTP-поведение, раньше
код этот заголовок игнорировал.

## Альтернативы и почему не они

- **Снять curl_cffi/маскировку раз есть разрешение** — отклонено: устное
  разрешение не меняет автоматическую конфигурацию Cloudflare на стороне
  KFF; риск бана на уровне инфраструктуры тот же, что и до разговора.
- **Отправлять идентифицирующий заголовок (`X-DOPX-Client`)** — первая
  версия этой правки его вводила, пользователь однозначно отклонил (см.
  пункт 0 решения выше) и убран целиком: разрешение — повод усилить
  маскировку, а не рисковать засветиться перед Cloudflare раньше времени.
- **Поднять частоту синка раз "можно"** — не сделано: пользователь просил
  стабильность, не объём; расписание tight/loose (см. `parsers/tasks.py`,
  правка того же дня) уже разумно, увеличивать нагрузку без явного запроса
  — плохая идея именно в контексте "чтобы блокировок не было".
  Возможность вернуться к более частому прогону остаётся, если появится
  формальный whitelist от KFF.
- **Удалить `parsers/kff/referee_scraper.py`** — рассмотрено (он тоже
  ходит на kffleague.kz без защиты), но НЕ тронуто: файл подтверждённо
  мёртвый код (0 вызовов во всём проекте, грепом), URL в нём уже не
  существует, прошлый аудит рекомендовал удаление, но удаление файлов в
  подключённой папке требует отдельного явного разрешения пользователя
  (`allow_cowork_file_delete`) — вне рамок этого запроса, отдельно не
  вызывалось.

## Последствия

- Оба пути к kffleague.kz (JSON API и HTML-скрапинг) теперь под одной
  защитой — блокировка через один немедленно останавливает второй.
- Ложные срабатывания circuit breaker'а от обычных 404 больше невозможны —
  проверено юнит-тестами против самого продакшен-файла (см. ниже).
- 429 с `Retry-After` обрабатывается по HTTP-стандарту, а не собственным
  фиксированным таймером.
- С точки зрения Cloudflare/KFF клиент неотличим от того, каким был до
  всего этого разговора (никакого нового заголовка) — единственное, что
  изменилось технически снаружи, ничего.
- Верификация: `parsers/kff/client.py`/`photo_scraper.py`/`tasks.py`/
  `settings.py` — `py_compile` чисто. Реальная логика circuit breaker
  (`check_kff_circuit_breaker`/`register_kff_success`/`register_kff_failure`,
  включая полный `KFFClient._get()`) прогнана через standalone-скрипт,
  загружающий САМ файл `client.py` через `importlib` с застабленным
  `django.core.cache`/`django.conf.settings` (тот же приём, что уже
  использовался в этой сессии для Pillow-кода) — подтверждено: 404 не
  копится в счётчике неудач даже после 10 подряд, 403 всё ещё копится и
  triggers cooldown ровно на 5-й раз, `Retry-After` уважается и капается
  30 секундами; после удаления заголовка отдельно перепроверено —
  `kff_identity_headers` больше не существует, `X-DOPX-Client` нигде не
  добавляется, curl_cffi (`impersonate="chrome"`) и порог/cooldown circuit
  breaker'а — без изменений.
