# 0039 — Ещё две меры против блокировок: cookie jar + глобальный pacing

Дата: 2026-09-07
Статус: Accepted

## Контекст

Прямой запрос после ADR 0038: "придумай как ещё дополнительно можно
защититься от блокировок. может есть библиотеки какие-то которые ещё более
стабильным сделают наш парсер".

Проверил установленную версию `curl_cffi` (0.16.2, `requirements.txt`) —
алиас `impersonate="chrome"` в этой версии резолвится в `chrome150`,
самый свежий доступный профиль пакета: TLS/HTTP2-имперсонация уже
максимально актуальна, апгрейд библиотеки тут не нужен. Проверил внешний
поиск (2026) по теме — стандартный плейбук против Cloudflare Bot
Management: (1) TLS/JA3-отпечаток — уже закрыто curl_cffi, (2) IP-
репутация — Cloudflare флагает диапазоны облачных провайдеров (AWS,
DigitalOcean и т.п.) независимо от TLS-отпечатка, а `docs/DEPLOYMENT.md`
прямо рекомендует деплой на VPS (DigitalOcean/Timeweb/Selectel) — то есть
это единственный слой риска, который НЕ решается кодом вообще, только
резидентным прокси (платно, отдельное решение) или явным IP-whitelist от
KFF, раз разрешение уже есть. Дополнительно проверил
`https://kffleague.kz/robots.txt` — `Disallow: /api/` присутствует
буквально для эндпоинта, которым пользуется `KFFClient`; устное
разрешение конкретного человека перекрывает это как более сильный сигнал,
но сам факт стоит держать в голове как контекст, почему Cloudflare мог
исторически быть особенно придирчив именно к `/api/*`.

Библиотечных апгрейдов не потребовалось — обе новые меры реализованы на
том, что уже есть в проекте (Django cache/Redis), без новых зависимостей.

## Решение

### 1. Cookie jar persistence через Redis

`load_kff_cookies(session)` / `save_kff_cookies(session)`
(`parsers/kff/client.py`) — общий для JSON API и HTML-скрапинга Redis-ключ
`kff_api:session_cookies` (TTL 6 часов, продлевается на каждый успешный
ответ). Настоящий браузер держит один набор cookies (включая
Cloudflare `__cf_bm`/`cf_clearance`, если хост когда-либо их выставит)
часами; у нас же `parsers/kff/pipeline.py::_import_full_match_locked`
создаёт НОВЫЙ `KFFClient()` на КАЖДЫЙ матч — в рамках одного прогона
`sync_season` по 60+ матчам это выглядело как 60+ независимых "первых
визитов" подряд, а не один клиент с долгой сессией. `load_kff_cookies`
вызывается в `KFFClient.__init__` и `photo_scraper._session()` сразу после
создания session; `save_kff_cookies` — после КАЖДОГО успешного или
"обычного" (не блокирующего) ответа, не только первого — cookie от
Cloudflare может прийти не с первого ответа.

Обе функции защищены `try/except`: cookies — полезная добавка, не
обязательное условие запроса, ошибка сериализации/десериализации не
должна ронять сам запрос.

### 2. Глобальный pacing gate — курс на ВСЕ воркеры разом

Джиттер внутри `_get()` (0.3–0.9с) выравнивает интервал между запросами
ОДНОГО `session`, но не защищает от того, что ДВА РАЗНЫХ расписания
(`update-live-matches` каждые 2 мин и `update-upcoming-matches-full`
каждые 30 мин — совпадают каждые полчаса) сработают ПАРАЛЛЕЛЬНО и
одновременно откроют запросы с разных TCP-соединений. Одновременный
трафик с нескольких соединений — отдельный поведенческий сигнал,
человек физически не открывает две вкладки с идеальной синхронностью.

`global_pace_gate()` (`parsers/kff/client.py`) — общий Redis-таймстамп
"когда был последний запрос к ЛЮБОМУ URL на kffleague.kz, из ЛЮБОЙ
задачи/воркера" (`kff_api:global_pace:last_request_at`, TTL 30с). Перед
каждой попыткой `_get()`/`_fetch_html()`/`download_photo_bytes()` — если с
прошлого запроса (откуда бы он ни пришёл) не прошло 0.35с, ждём разницу.
Не строгий семафор (не гарантирует нулевую гонку под экстремальной
параллельностью), а courtesy-throttle того же уровня строгости, что и
circuit breaker — для десятков последовательных запросов Celery beat
этого достаточно.

## Альтернативы и почему не они

- **Обновить/сменить библиотеку TLS-имперсонации** — не нужно: `curl_cffi`
  0.16.2 уже резолвит `"chrome"` в `chrome150`, актуальнейший доступный
  профиль. Апгрейд пакета ничего не даст прямо сейчас.
- **Headless-браузер (Playwright/nodriver) вместо curl_cffi** — отклонено:
  нужен только при JS-challenge/Turnstile, а KFF отдаёт обычный SSR без
  JS (подтверждено вручную ещё в 2026-08-21, см. докстринг
  `photo_scraper.py`). Резервный вариант, ЕСЛИ Cloudflare когда-нибудь
  включит JS-challenge конкретно для нас — не сейчас: тяжелее, медленнее,
  новая зависимость на пустом месте.
- **Резидентные прокси для IP-репутации** — не реализовано: платная
  инфраструктурная закупка, отдельное решение пользователя, не код.
  Технически это единственный слой, который код принципиально не может
  закрыть (см. Контекст выше) — если блокировки продолжатся несмотря на
  всё сделанное, следующий шаг именно этот, либо прямой IP-whitelist от
  KFF (раз разрешение уже устно есть).
- **`tenacity`/сторонняя библиотека ретраев** — не добавлена: текущая
  ручная retry-логика с классификацией по коду ответа уже специфична под
  circuit breaker/cookie/pacing-гейты этого модуля; обёртывание в
  сторонний декоратор добавило бы зависимость без содержательного
  выигрыша над уже работающим и покрытым тестами кодом.

## Последствия

- Ни один из путей к kffleague.kz больше не выглядит как одноразовый
  "анонимный" клиент — сессия логически продолжается между отдельными
  `KFFClient()`/`photo_scraper._session()`, как у настоящего браузера.
- Два независимых расписания синка физически не могут ударить по хосту
  одновременно с разных соединений — минимальный зазор гарантирован
  общим состоянием в Redis, а не только внутри одного клиента.
- Явный потолок того, что решается кодом: IP-репутация облачного
  хостинга — фактор, зафиксированный в этом ADR как открытый риск, а не
  замолченная деталь.
- Верификация: `py_compile` всех тронутых файлов чисто. Новая логика
  (`load_kff_cookies`/`save_kff_cookies`/`global_pace_gate`) прогнана
  через тот же приём — `importlib` загружает САМ файл `client.py` с
  застабленным `django.core.cache` — подтверждено: cookies переживают
  пересоздание session, `load_kff_cookies`/`save_kff_cookies` не падают
  на "сломанных" cookie-объектах, `global_pace_gate` заставляет
  спонтанный второй вызов подождать ~0.35с и не ждёт вовсе, если реальное
  время между запросами уже больше порога. Полный `KFFClient._get()`
  перепрогнан с новыми гейтами — успешный ответ сохраняет cookies,
  circuit breaker по-прежнему триггерится на 5-й подряд 403, cooldown
  по-прежнему обрывает цикл до сетевого вызова. `photo_scraper.py`
  импортируется чисто с новыми именами.
