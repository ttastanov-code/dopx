# 0004 — План перехода live-страниц с поллинга на SSE

Дата: 2026-09-04
Статус: Accepted (план подготовлен, реализация — ПОСЛЕ решения по
production ASGI/worker-стратегии, не раньше)

## Контекст

Live-обновления сейчас — HTMX-поллинг с фиксированным интервалом:
`templates/matches/_match_events.html` (события матча, каждые 15с),
`templates/matches/_match_header.html` (счёт/статус, каждые 20с),
`templates/components/_notification_unread_badge.html` (30с), плюс
несколько staff-дашбордов (10-20с). Внешний аудит справедливо отмечает: при
росте одновременных зрителей одного live-матча это O(зрители × 1/15с)
запросов на один и тот же в основном неизменный ответ — расточительно и для
сервера, и для батареи телефона зрителя.

## Почему это НЕ делается прямо сейчас, а только проектируется

`docker-compose.yml`/`Dockerfile` сейчас запускают Django через `gunicorn` с
СИНХРОННЫМИ воркерами (WSGI). Sever-Sent Events — это HTTP-соединение,
которое сервер держит открытым и пишет в него по мере появления новых
данных: на синхронном воркере ОДНО такое соединение занимает ОДИН воркер
на всё время, пока клиент слушает — при 20+ зрителях одного live-матча
исчерпание пула воркеров наступит быстрее, чем при обычном поллинге (то же
самое соединение, но КОРОТКОЕ, воркер освобождается сразу после ответа).
Иначе говоря: реализовать SSE поверх текущей `gunicorn`-конфигурации без
смены класса воркера (`sync` → `gevent`/`uvicorn.workers.UvicornWorker` +
перевод `dopx/asgi.py` в фактическое использование, если ещё не используется)
означало бы обменять один известный риск масштабирования на другой, менее
предсказуемый — и именно эту смену воркер-класса ещё нет причин делать
вслепую в локальной разработке: она напрямую завязана на то, как будет
устроен production nginx/Docker-стек, то есть ровно то самое "нужно будет
менять после деплоя", чего просили избегать.

## Решение (план, не код)

Когда встанет вопрос production-инфраструктуры:

1. Сменить `gunicorn` worker class на `gevent` (минимальное изменение —
   тот же WSGI-код, `pip install gevent`, `--worker-class gevent` в
   команде запуска) ИЛИ перевести на `uvicorn`/ASGI, если к этому моменту
   уже понадобится Django Channels для чего-то ещё (push непосредственно
   в браузер, не только SSE). Не решать заранее globally — брать
   минимально достаточный вариант под SSE отдельно от гипотетических
   будущих WebSocket-фич.
2. Один SSE-эндпоинт на матч (`/matches/<id>/events/stream/`), не общий на
   все live-матчи разом — клиент подписан только на то, что реально
   смотрит.
3. Источник событий на бэкенде — тот же путь, что уже пишет `MatchEvent`
   (`parsers/tasks.py::update_match_statuses` → `import_events_and_minutes`)
   публикует в Redis Pub/Sub канал `match:<id>:events` при
   `on_event_created` (тот же коллбэк, что уже используется для push-
   уведомлений о голах — см. `notify_followers_match_event`, просто ещё
   один подписчик того же события).
4. HTMX уже поддерживает SSE через официальное расширение
   `htmx-ext-sse` — замена `hx-trigger="every 15s"` на
   `hx-ext="sse" sse-connect="..." sse-swap="..."` не требует переписывать
   остальной HTML/партиалы, только сам механизм доставки. Полёт "малой
   кровью" для существующего кода.
5. nginx — требуется `proxy_buffering off` и увеличенный `proxy_read_timeout`
   именно для location этого эндпоинта — единственная правка на стороне
   веб-сервера, которую нужно будет сделать в проде одновременно.
6. Поллинг остаётся для ВСЕГО остального (staff-дашборды, счётчик
   уведомлений) — там нагрузка на порядки меньше (один staff, не тысяча
   зрителей), переусложнять незачем.

## Альтернативы и почему не они (пока)

- **WebSocket вместо SSE** — отклонено для этой конкретной задачи: обмен
  здесь односторонний (сервер → клиент), SSE специально для этого проще
  (переживает разрыв соединения и переподключается сам, работает поверх
  обычного HTTP, не нужен отдельный протокол/порт). WebSocket
  рассматривать отдельно, если появится сценарий с обратным каналом
  (например, живой чат зрителей матча).
- **Оставить поллинг навсегда** — отклонено как решение НАВСЕГДА, но не
  меняется прямо сейчас: нагрузка ещё далека от точки, где это станет
  реальной проблемой (счёт пользователей, не десятки тысяч на один матч
  одновременно).

## Последствия

Пока ничего не меняется в коде. Триггер к реализации — конкретное решение
по production Docker/nginx-стеку (см. `docs/DEPLOYMENT.md`), делать это
нужно одним заходом вместе со сменой worker-класса gunicorn, не раньше.
