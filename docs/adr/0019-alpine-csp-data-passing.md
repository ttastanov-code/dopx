# 0019 — Динамические строки в Alpine x-data идут через data-атрибуты, не escapejs()

Дата: 2026-08-21
Статус: Accepted

## Контекст

Обнаружено на конкретном баге: тултип для дерби-пар рендерил
"Дербии002Дэксперт" вместо "Дерби-эксперт". Текст шёл через `escapejs()`
прямо в строковый литерал внутри `x-data="tooltipTrigger('...')"`.
`escapejs()` экранирует дефис как `-` (см.
`django.utils.html._js_escapes`) — валидный JS для настоящего движка, но
CSP-сборка Alpine (`@alpinejs/csp`, обязательная под `script-src` без
`'unsafe-eval'`) разбирает выражение `x-data` собственным парсером, не
через настоящий JS-движок, и не раскрывает `\uXXXX`-последовательности
внутри строковых литералов аргумента — экранированные символы утекали в
текст как есть.

Тот же класс бага повторно всплыл в `templates/evaluations/context.html`:
`supported_team` (UUID команды, содержит дефисы) шёл тем же путём в
аргумент `matchContextForm(...)`, из-за чего `supportedTeam` мог тихо не
совпадать с `value` радиокнопок.

## Решение

Не передавать динамический текст аргументом функции в `x-data` вообще —
класть его в обычный HTML `data-`атрибут (экранируется штатным HTML-
`escape()`, никакого JS-парсинга) и читать в `init()` компонента через
`this.$el.dataset` (см. `tooltipTrigger` в `alpine-components.js`,
`matchContextForm` — то же самое для `data-supported-team`/
`data-watched-type`/`data-attended-stadium`/`data-eval-mode`).

## Последствия

- Правило для всего проекта: любой Alpine-компонент, которому нужны
  начальные значения из Django-контекста, читает их из `data-`атрибутов
  корневого элемента в `init()`, а не принимает строковыми аргументами
  вызова `x-data="component('...')"`. Аргументы функции в `x-data`
  допустимы только для статических/безопасных литералов (булевы флаги,
  ID без спецсимволов), не для произвольного текста/UUID пользовательских
  данных.
