# 0003 — Миграции как отдельный, видимый шаг деплоя

Дата: 2026-09-04
Статус: Accepted

## Контекст

`docker/entrypoint.sh` накатывает миграции на КАЖДОМ старте `web`-контейнера
(команда `gunicorn`) — осознанный компромисс для одного сервера с ручным
SSH-деплоем (см. комментарий в самом файле). Внешний аудит справедливо
отметил риск с ростом: если миграция упадёт или окажется несовместимой со
старым кодом, который какое-то время ещё может обслуживать трафик при
rolling-обновлении, сбой обнаружится только по логам контейнера, а не как
явный красный шаг деплоя.

Полная реализация "отдельного deploy-job" в духе больших команд (blue-green,
canary, миграции в отдельном Kubernetes Job) на нынешнем масштабе (один
сервер, `docker compose`, деплой не чаще нескольких раз в день) избыточна и
ничего не выигрывает — переусложнение ради переусложнения.

## Решение

`.github/workflows/deploy.yml`, job `deploy` — три отдельных, видимых в логе
Actions шага вместо одного `docker compose up -d --build`:

1. `docker compose build web celery celery-beat` — сборка отдельно от
   запуска.
2. `docker compose run --rm web python manage.py migrate --noinput` —
   миграция ОДНОРАЗОВЫМ контейнером на уже собранном образе, ДО перезапуска
   `web`. `docker compose run` переопределяет только CMD, не ENTRYPOINT —
   `docker/entrypoint.sh` по-прежнему ждёт доступности БД перед тем, как
   выполнить переданную команду; ветка `case "$1" in gunicorn)` не
   срабатывает для `python`, так что миграция выполняется ровно один раз, а
   не дважды с разной логикой. `set -e` в скрипте деплоя останавливает всё
   на этом шаге, если миграция упала — старые контейнеры продолжают
   работать на старой схеме, а не переходят в промежуточное состояние.
3. `docker compose up -d --build` + смоук-тест (`curl` по `/admin/login/` с
   5 попытками и паузой) — деплой считается успешным только если сайт
   реально отвечает после перезапуска, не просто "контейнер в состоянии
   running".

`docker/entrypoint.sh` НЕ изменён — миграция там остаётся как было. Это
специально: локальная разработка и `docker compose up` продолжают работать
без единой лишней команды (см. Альтернативы ниже), а на проде эта же строка
теперь просто идемпотентно проверяет "миграции уже применены" (Django сам
не переприменяет уже накатанные миграции) — не вредит, но и не единственная
линия защиты, как было раньше.

## Альтернативы и почему не они

- **Убрать миграцию из entrypoint.sh совсем** — отклонено: это меняло бы
  поведение `docker compose up` для локальной разработки (пришлось бы
  отдельно помнить прогнать миграции руками после каждого pull) — именно
  то изменение, которого просили избежать ("не ломать текущий локальный
  сервер"). Оставлена как есть, деплой получил свою независимую копию шага.
- **Kubernetes Job / отдельный CI-раннер для миграций** — отклонено:
  инфраструктура для одного Docker Compose сервера, добавление K8s было бы
  решением несуществующей сейчас проблемы масштаба.

## Последствия

- Деплой на прод (когда появится сервер и секреты) — упавшая миграция
  останавливает деплой ДО того, как новый код увидит пользователь, с
  понятным красным шагом в GitHub Actions вместо необходимости читать логи
  контейнера на сервере.
- Локальная разработка — без изменений.
