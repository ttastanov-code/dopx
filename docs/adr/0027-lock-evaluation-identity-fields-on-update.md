# 0027 — Identity-поля оценок нельзя менять после создания

Дата: 2026-09-07
Статус: Accepted

## Контекст

Второй раунд внешнего аудита (`docs/CODEX_AUDIT_RESPONSE_2026-09-07.md`)
нашёл дыру в том же слое, который ADR-0001 уже закрывал для `POST`:
`EvaluationPolicy` (принадлежность игрока/команды/тренера матчу) реально
проверяется в `api/serializers.py::*Serializer.validate()`, но там сущности
берутся через `data.get("match")`/`data.get("player")` и т.д.

При частичном обновлении (`PATCH`) DRF кладёт в `data` только те поля,
которые реально пришли в теле запроса. Если PATCH меняет, например, только
`player`, не передавая `match` — `data.get("match")` возвращает `None`, и
весь блок `if user and match: ...` (внутри которого и вызывается
`assert_player_in_squad`) молча пропускается целиком, вместе с проверкой
уникальности. Практическое следствие: владелец собственной оценки мог
честно создать её через `POST`, а затем прямым `PATCH` подменить
`match`/`player`/`team`/`coach`/`supported_team` на что угодно — агрегаты и
сезонная сборная не отличили бы такую запись от настоящей.

Дополнительно найдена смежная несогласованность: `assert_context_exists`
(контекст просмотра матча — шаг 1 вайзарда) вызывался в `validate()` только
для `PlayerEvaluationSerializer`/`TeamEvaluationSerializer`, но не для
`CoachEvaluationSerializer`/`RefereeEvaluationSerializer`/
`MatchEvaluationSerializer` — прямой POST в API мог оценить тренера/судью/
матч в целом, ни разу не подтвердив, что вообще смотрел игру.

## Решение

**1. Identity-поля запрещено менять после создания.** Новая функция
`api/serializers.py::_forbid_identity_field_changes(instance, data,
field_names)` — если `self.instance` уже существует (это `PATCH`/`PUT`, не
`POST`) и любое из перечисленных полей ПРИСУТСТВУЕТ в `data` со значением,
отличным от текущего, `validate()` поднимает `ValidationError` до того, как
дело дойдёт до `EvaluationPolicy`. После создания разрешено менять только
сами баллы (`contribution`/`tactics`/`influence_score` и т.п.) — то, ради
чего вообще существует `PATCH` в этом API (поправить оценку, не пересоздавая
её). Подключено во ВСЕХ шести `validate()`:

  - `ContextEvaluationSerializer` — `("match", "supported_team")`
  - `PlayerEvaluationSerializer` — `("match", "player")`
  - `TeamEvaluationSerializer` — `("match", "team")`
  - `CoachEvaluationSerializer` — `("match", "coach")`
  - `RefereeEvaluationSerializer` — `("match",)`
  - `MatchEvaluationSerializer` — `("match",)`

Это устраняет не только исходный сценарий (identity-поле отсутствует в
`data`, проверка пропускается), но и вариант, который сама по себе починка
`data.get()` не закрыла бы: явную попытку подменить поле значением,
которое само по себе ВАЛИДНО (например, другой игрок из ТОЙ ЖЕ заявки) —
`EvaluationPolicy` такую подмену пропустила бы, раз оба игрока реально в
составе. Проще запретить менять личность оценки вообще, чем пытаться
угадать, какая передача имеет "легитимную" причину.

**2. Контекст просмотра — обязателен для всех пяти типов предметных
оценок, не только Player/Team.** `assert_context_exists` теперь вызывается
(при создании, `if not self.instance`) и в `CoachEvaluationSerializer`, и в
`RefereeEvaluationSerializer`, и в `MatchEvaluationSerializer` — тем же
паттерном, что уже был у Player/Team. HTML-вайзард это правило и так
соблюдал структурно (контекст — шаг 1, дальше пути назад нет), правило
касалось только прямых обращений к API в обход вайзарда.

## Альтернативы и почему не они

- **Просто поправить `data.get()` на явную проверку "ключ есть, но
  сравнить со старым значением"** — рассмотрено, отклонено: пришлось бы
  дублировать эту логику в каждом `validate()` заново и держать в голове,
  что она обязательна при добавлении любого нового identity-поля в будущем.
  Общая функция с явным списком полей — один способ ошибиться (забыть
  вызвать её для нового сериалайзера), а не N способов.
- **Разрешить менять identity-поля, но перепроверять `EvaluationPolicy`
  заново при каждом PATCH** — отклонено: не даёт ничего, что не даёт
  создание новой оценки, зато сохраняет риск ретроактивной подмены
  сущности в исторических агрегатах/антифрод-сигналах (например,
  `ContextEvaluation.supported_team` используется для own/rival-сегментации
  в `aggregates/services.py` — смена команды поддержки задним числом сдвинула
  бы уже посчитанную историческую сегментацию).

## Последствия

- API-клиент, которому нужно "исправить" оценку не тех сущностей, должен
  удалить неверную запись (`DELETE`) и создать новую (`POST`), а не
  PATCH'ить identity-поля — это ожидаемое ограничение, не баг.
- Тесты: `api/tests.py::EvaluationIdentityImmutableOnUpdateAPITests` (по
  одному тесту на каждый из 6 типов + контрольный тест, что PATCH баллов
  по-прежнему работает), `EvaluationPolicyAPITests::test_*_without_context_rejected`
  (coach/referee/match).
- Любой НОВЫЙ сериалайзер оценки с identity-полем (матч + оцениваемая
  сущность) обязан вызывать `_forbid_identity_field_changes` в своём
  `validate()` — иначе он унаследует ровно ту же дыру.
