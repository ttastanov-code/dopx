# 0001 — EvaluationPolicy: единая точка правды для правил голосования

Дата: 2026-09-04
Статус: Accepted

## Контекст

Внешний аудит (ChatGPT Codex, см. `docs/CODEX_AUDIT_RESPONSE_2026-09-04.md`)
обнаружил, что правила допустимости оценки были продублированы в двух
независимых местах и разошлись:

- `evaluations/forms.py` — веб-визард безопасен КОНСТРУКТИВНО: querysets и
  способ генерации полей формы физически не позволяют подставить сущность,
  не относящуюся к матчу (например, `PlayerEvaluationForm` создаёт поля
  только для игроков реального состава — `MatchLineupPlayer.objects.filter(
  lineup__match=self.match)`).
- `api/serializers.py` — DRF-сериалайзеры принимали `player`/`team`/`coach`
  как произвольный ID из тела запроса и проверяли только: (1) окно
  голосования открыто, (2) пользователь ещё не голосовал за эту пару
  (уникальность), (3) контекст просмотра создан. Принадлежность сущности
  МАТЧУ не проверялась вообще.

Следствие: верифицированный пользователь мог прямым POST в API (в обход
html-визарда) поставить оценку игроку/команде/тренеру, не участвовавшим в
конкретном матче. Это напрямую портит агрегаты, тур и сезонную сборную —
не гипотетически, а причём без какого-либо взлома, только знанием
публичной схемы API (она и так открыта через `drf-spectacular`).

## Решение

Создан `evaluations/policies.py` — набор `assert_*`-функций
(`assert_voting_open`, `assert_context_exists`, `assert_team_in_match`,
`assert_player_in_squad`, `assert_coach_in_match`), каждая либо молча
проходит, либо поднимает единое исключение `EvaluationPolicyError` с
готовым пользовательским текстом.

`api/serializers.py` — все шесть `validate()`/`validate_match()` теперь
вызывают эти функции вместо продублированной инлайн-логики.

`evaluations/forms.py` — `ContextEvaluationForm.clean_supported_team()`
тоже вызывает `assert_team_in_match` как второй, избыточный на сегодня
слой защиты: сейчас это уже гарантировано queryset'ом
(`ModelChoiceField` сам отклонит значение вне queryset), но если в будущем
кто-то по невнимательности расширит queryset — политика всё равно поймает
нарушение. Остальные формы (`TeamEvaluationForm`/`PlayerEvaluationForm`/
`CoachEvaluationForm`) НЕ вызывают политику — там в принципе невозможно
отправить чужой ID: поля формы генерируются по реальным сущностям матча, и
view читает `cleaned_data` только по именам полей, которые сам же
сгенерировал из реального состава/тренеров. Вызывать политику там было бы
проверкой того, что и так недостижимо — ложное чувство защиты вместо
реальной пользы.

## Альтернативы и почему не они

- **Полный переход на слой `selectors/services/policies` для всего
  проекта** (как предлагал внешний аудит) — правильное направление в
  целом, но отклонено для ЭТОЙ конкретной задачи: это рефакторинг всего
  домена оценок/агрегатов/матчей одним заходом, без доступа к реальному
  Django для прогона тестов в песочнице разработки риск регресса
  неприемлемо высокий относительно выигрыша. `EvaluationPolicy` — узкий,
  проверяемый шаг в эту сторону; расширять на другие домены — когда
  появится второй похожий случай дублирования правил, оправдывающий более
  широкий рефакторинг.
- **DB-уровень (FK-констрейнт "player must be in squad")** — отклонено:
  такое ограничение невозможно выразить обычным `ForeignKey`/`CheckConstraint`
  в PostgreSQL без денормализации (проверка требует JOIN через
  `MatchLineupPlayer`), потребовало бы триггера — сложнее для чтения и
  тестирования, чем явная функция на уровне приложения.

## Последствия

- Новое правило голосования добавляется ОДИН раз в
  `evaluations/policies.py`, а не ищется по всем местам, где могло быть
  продублировано.
- API теперь возвращает `400` с понятным текстом на попытку оценить
  сущность не из этого матча (было — `201 Created`, тихая порча агрегатов).
- Тесты на каждый тип нарушения — в `api/tests.py`
  (`EvaluationPolicyAPITests`).
