# 0005 — Анти-шум: отслеживание "тронутых" ползунков в вайзарде оценки

Дата: 2026-09-04
Статус: Accepted

## Контекст

При разборе внешнего аудита (см. `docs/CODEX_AUDIT_RESPONSE_2026-09-04.md`,
раздел про "не показывать 8.7 против 8.6 без учёта выборки") обнаружена
проблема на шаг раньше проблемы, которую поднимал аудит: часть выборки
может быть не просто маленькой, а шумной.

`<input type="range">` физически не может остаться пустым при отправке
формы — браузер всегда шлёт какое-то значение, даже если пользователь ни
разу не подвинул ползунок. Во всех пяти формах вайзарда (Teams/Coaches/
Referee/Players/MatchFinal) каждый критерий рендерился с `value="5"`
(середина шкалы) — пользователь, кликающий "Далее" по всем шести шагам не
глядя, отправлял столько же валидных данных, сколько тот, кто реально
обдумал каждую оценку. Со стороны агрегатов эти два случая неразличимы.

## Решение

**Клиент** (`static/js/wizard-sliders.js`): единый делегированный слушатель,
уже существовавший в файле для заливки трека слайдера (`--wz-fill`),
расширен так, чтобы на каждый `.wizard-slider` заводить скрытое поле-спутник
`"<name>__touched"` (`"0"` изначально, `"1"` после первого реального
`input`-события) и визуальную подсказку (`static/css/wizard.css`,
`.wz-slider-card--untouched`) — тусклый бегунок и текст-подсказка, пока
критерий не тронут. Работает для ВСЕХ пяти форм без единой правки разметки
самих полей — тот же архитектурный приём, что уже использовался в этом
файле для `--wz-fill` (один делегированный обработчик на класс, а не
переписывание каждого шаблона).

**Сервер** (`evaluations/views.py::_touched_fields`): по списку имён полей
возвращает те, что реально были тронуты. Используется в
`EvaluateTeamsView.post`, `EvaluateCoachesView.post`,
`EvaluateRefereeView.form_valid`, `EvaluatePlayersView.post` — если у
сущности (команда/тренер/матч официальный/игрок) НИ ОДИН критерий не
тронут, запись (`TeamEvaluation`/`CoachEvaluation`/`RefereeEvaluation`/
`PlayerEvaluation`) вообще не создаётся, вместо того чтобы сохраниться со
значениями по умолчанию.

**Деградация без JS**: если для группы полей в POST вообще нет ни одного
`"__touched"`-парного поля (JS не выполнился), `_touched_fields` считает
ВСЕ поля тронутыми — форма продолжает работать как раньше, просто без
анти-шум фильтра. Без этой защиты пользователи с отключённым JS молча
теряли бы каждую честно выставленную оценку.

**Шаг "Общая оценка матча" (MatchFinal) — сознательно НЕ включён в
skip-логику.** Это финальный, завершающий вайзард шаг, наглухо связанный в
одной транзакции с начислением XP, корректировкой Trust Score, streak’ами и
бейджами (`EvaluateMatchFinalView.form_valid`) — расцеплять создание
`MatchEvaluation` от факта "вайзард пройден" означало бы трогать эту
завязанную логику ради шага, где сигнал 4 полей на 1 сущность объективно
менее критичен, чем на остальных четырёх шагах (десятки записей на
сущность). Визуальная подсказка на этой странице всё равно показывается
(нейтральный текст по умолчанию из `wizard-sliders.js`, без утверждения
"иначе не засчитается" — там оно было бы неправдой).

## Альтернативы и почему не они

- **Убрать `value="5"` совсем** — не работает: `<input type="range">`
  всегда имеет какое-то значение, атрибут `value` лишь задаёт начальную
  позицию, оставить его пустым нельзя технически.
- **Заменить слайдеры на 10 отдельных кнопок/радио без предвыбранного
  значения** — рассмотрено и отклонено для этой правки: реальный
  UI-редизайн всех пяти форм, тогда как текущее решение чинит проблему без
  единой правки разметки полей. Не исключено на будущее, если анти-шум
  через touched-tracking окажется недостаточно понятным пользователям на
  практике — тогда это следующий кандидат.
- **Требовать явное подтверждение (чекбокс "я закончил оценивать") на весь
  шаг разом** — отклонено: грубее, чем по-критериям, не даёт сохранить
  честно выставленные 3 из 4 критериев, если четвёртый пользователь
  действительно оставил как есть осознанно.

## Последствия

- Существующие данные, накопленные ДО этой правки, не ретроактивно
  помечены — у нас нет способа отличить задним числом реальную "5" от
  неосознанной. Это не восстановить, только не приумножать вперёд.
- Тесты: `evaluations/tests.py::AntiNoiseTouchedTrackingTests` — три сценария
  (ничего не тронуто → 0 записей; один критерий тронут → сохраняется только
  соответствующая сущность; нет JS вообще → полная деградация к старому
  поведению).
