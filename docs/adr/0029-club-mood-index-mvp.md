# 0029 — Индекс настроения клуба: MVP тренд-бейдж

Дата: 2026-09-07
Статус: Accepted

## Контекст

`docs/PRODUCT_SCOPE_MATCH_DNA_AND_EXPLAINABILITY.md` (раздел 3) — самая
дорогая и самая репутационно чувствительная из трёх идей: полноценная
версия требует новой модели снимков, периодической Celery-задачи и
time-series визуализации, которой в проекте пока нигде нет. Сам
scope-документ рекомендовал НЕ строить сразу полную версию, а сначала
проверить продуктовую гипотезу дёшево — MVP тренд-бейдж без новой модели.

## Решение

`teams/services.py::compute_mood_trend(team)` — чистая функция без новой
модели и без Celery:

- Берёт последние `MOOD_TREND_RECENT_MATCHES = 5` строк
  `TeamMatchAggregate` команды с `total_votes > 0`
  (`Meta.ordering = ['-match__start_time']` уже даёт нужный порядок без
  дополнительной сортировки).
- Меньше 2 строк — сравнивать не с чем, `None` (бейдж не рендерится).
- Направление считается сравнением среднего `performance_score` более
  свежей половины окна с более старой (не "первый минус последний" —
  один выброс на краю окна не должен единолично решать направление).
  Порог `MOOD_TREND_NOISE_THRESHOLD = 0.3` — разница меньше считается
  шумом ("стабильно"), не трендом.
- Результат кэшируется на `MOOD_TREND_CACHE_TIMEOUT = 3600` секунд —
  агрегаты и так пересчитываются асинхронно не мгновенно, реалтайм здесь
  не нужен, кэш просто избавляет от лишнего запроса на каждый рендер
  страницы команды. `cache.get(key, "__unset__")` — сентинел вместо
  дефолтного `None`, иначе легитимный кэшированный результат "недостаточно
  данных" (`None`) каждый раз считался бы заново.
- Бейдж (↑ "Растёт" / ↓ "Падает" / → "Стабильно") — в шапке страницы
  команды (`templates/teams/detail.html`), рядом с названием и кнопкой
  "Подписаться".

## Альтернативы и почему не они

- **Полноценный индекс с историей сразу** — отклонено по прямой
  рекомендации scope-документа: психологическая метрика "настроение"
  достаточно спекулятивна, чтобы рискнуть спроектировать не ту схему
  хранения при первом заходе. Дешёвый MVP без модели — способ проверить
  интерес пользователей до необратимых архитектурных решений.
- **own_fans_avg/rival_fans_avg как прокси "внутреннего недовольства"**
  (упомянуто в scope-документе как возможное направление) — НЕ включено в
  этот MVP: усложнило бы первую версию сразу двумя сигналами вместо
  одного, при этом сам scope-документ отдельно предупреждал о риске
  систематического перекоса в пользу топ-клубов — такой сигнал стоит
  добавлять только после того, как простой тренд-бейдж пройдёт проверку.

## Последствия

- Ни новой модели, ни миграции, ни Celery-задачи — при необходимости
  полноценной версии (time-series, история, публичный график) это будет
  отдельное решение с отдельной ADR, а не продолжение этой.
- Риск систематического перекоса в пользу топ-клубов (см. "Риск" в
  scope-документе) остаётся актуальным и для MVP-версии — если бейдж
  окажется заметно "радующим" топ-клубы и "расстраивающим" аутсайдеров
  вне зависимости от объективной формы команды, это сигнал не публиковать
  полную версию без дополнительной защиты (например, тот же
  neutral-anchor принцип, что уже есть в `aggregates/services.py` для
  performance_score).
- Тест: `teams/tests.py::MoodTrendServiceTests` — направление/шум-порог/
  недостаточно данных.

## Addendum (2026-09-07, тот же день) — v2 реализован БЕЗ теневого прогона

`docs/adr/0034-club-mood-index-v2.md` реализовал полноценную версию
(time-series, own_fans_avg как отдельная метрика "доверие", связка с
`predictions`, B2B-фид) по прямому запросу пользователя. Явно и намеренно
НЕ выполнена собственная рекомендация этого документа и раздела "Риск"
scope-документа — "публиковать только после теневого прогона минимум один
полный круг чемпионата". Риск систематического перекоса в пользу
топ-клубов остаётся актуальным и НЕ проверенным экспериментально для v2 —
см. раздел "Последствия" ADR-0034. `compute_mood_trend` (бейдж, эта ADR)
не удалён — используется параллельно с графиком v2, не заменён им.
