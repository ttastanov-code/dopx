# 0020 — Дедуп уведомлений о результате прогноза: по факту отправки, не по факту записи

Дата: 2026-08-30 (Sentry-инцидент)
Статус: Accepted

## Контекст

`notify_prediction_results` (`notifications/tasks.py`) рассылает
уведомления о результате прогноза после завершения матча, дедуплицируя по
паре (пользователь, матч), чтобы не отправить письмо дважды. Дедуп
раньше смотрел на "есть ли вообще `Notification(prediction_result)` для
этой пары" — а `email_sent_at` проставлялся сразу при `bulk_create`, до
попытки реальной отправки письма.

Если письмо срывалось из-за сетевого сбоя (DNS/обрыв соединения — Sentry
поймал это, пока dev-сервер спал), запись всё равно оставалась "уже
уведомлён" навсегда — следующий прогон (через 30 минут) этого
пользователя больше никогда не трогал. Письмо терялось без возможности
когда-либо переотправиться.

## Решение

Дедуп — по уже отправленным (`email_sent_at` не пусто), а не по самому
факту существования записи `Notification`. Уже созданная, но не
отправленная (`email_sent_at` пуст) запись переиспользуется, чтобы не
плодить вторую in-app-строку на того же пользователя, и получает
`email_sent_at` только после реального успеха отправки.

Связано: `TRANSIENT_EMAIL_ERRORS` (та же область файла) классифицирует
сетевые/протокольные сбои (DNS, `ConnectionError`) как временные и
подлежащие повторной попытке — намеренно не голый `OSError` (перехватил
бы и файловые ошибки, не связанные с сетью) и не включает
`SMTPRecipientsRefused`/`SMTPSenderRefused`/`SMTPDataError` (постоянные
отказы, повторная попытка с теми же данными провалится так же).

## Последствия

- При добавлении новых типов рассылаемых уведомлений с похожим паттерном
  "разослать один раз после события" — использовать тот же принцип
  дедупа по факту успешной отправки, не по факту создания записи.
