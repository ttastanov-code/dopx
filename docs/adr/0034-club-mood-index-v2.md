# 0034 — Индекс настроения клуба v2: time series, доверие, ожидания, B2B

Дата: 2026-09-07
Статус: Accepted

## Контекст

ADR-0029 (MVP) сознательно ограничился одним бейджем-стрелкой (↑/↓/→) и
явно предупредил: "самая чувствительная из трёх идей репутационно...
публиковать только после теневого прогона минимум один полный круг
чемпионата". Прямой продуктовый запрос по итогам второго аудита требует
полноценную версию сейчас: "не 'оценка команды', а понятный график:
доверие болельщиков, ожидания перед матчем, реакция после матча, самые
спорные решения сезона... это будущий B2B-продукт для клубов и медиа —
только в агрегированном виде, без раскрытия пользователей".

Это ЯВНОЕ отклонение от собственной рекомендации ADR-0029 (теневой прогон
перед публикацией) — сделано по прямому запросу пользователя, а не
потому что риск систематического перекоса (топ-клубы выглядят лучше вне
зависимости от игры) перестал существовать. Риск остаётся
незадокументированным экспериментально, только описанным здесь.

## Решение

### Time series вместо одного бейджа (`compute_mood_series`)

`teams/services.py::compute_mood_trend` (v1, бейдж) НЕ удалён и НЕ
заменён — остаётся у заголовка страницы команды как быстрый ответ "как
дела прямо сейчас" (5 матчей). Новая `compute_mood_series` (10 матчей,
`MOOD_SERIES_MATCHES`) строит параллельный ряд из трёх метрик на общей
оси (позиция матча в списке, не дата — так пропуск в одном ряду, например
матч без прогнозов, не искажает позиции точек другого ряда):

- **mood** — `TeamMatchAggregate.performance_score` (общая "реакция после
  матча", свои+чужие+нейтралы вместе — та же метрика, что уже была в v1).
- **trust** — "доверие болельщиков", `TeamMatchAggregate.own_fans_avg`
  (ТОЛЬКО мнение своих же фанатов — не смешиваем с чужими/нейтралами,
  прямой ответ на пункт аудита "доверие болельщиков" как ОТДЕЛЬНАЯ метрика
  от общей оценки).
- **expectation_pct** — "ожидания перед матчем": доля прогнозов на победу
  ЭТОЙ команды среди всех `predictions.MatchPrediction` на этот матч, ДО
  игры. `None` (не 0%), если прогнозов не было вообще — отсутствие данных
  и "все прогнозировали и ошиблись" разные состояния.

Ключевое архитектурное решение: **не заводить новую модель/Celery-задачу**
для "ожиданий" — `predictions` уже есть в проекте (краудсорс 1X2 ДО матча,
ADR не заводился отдельно на момент этой правки), просто раньше никак не
связывался с индексом настроения. Реюз существующего приложения вместо
дублирования концепции "мнение до матча".

### SVG на сервере, не JS-библиотека (`build_sparkline_points`)

Координаты `<polyline>` считаются в Python (`teams/services.py`), шаблон
только вставляет готовую строку `points="..."` в инлайновый `<svg>`.
Сознательное продолжение ADR-0025 (убрали рантайм-зависимость от внешних
CDN, включая раньше используемый Chart.js) — новая фича с графиком НЕ
должна тихо вернуть внешнюю JS-зависимость обратно. Пропуски (`None`,
например `expectation_pct` без прогнозов) просто не попадают в
`coords` — линия рисуется отдельными видимыми сегментами вокруг разрыва
вместо интерполяции несуществующих данных.

### "Самые спорные решения сезона" (`find_season_controversial_matches`)

Сезонная агрегация уже существующего сигнала
`RefereeMatchAggregate.home_fans_avg`/`away_fans_avg` (тот же, что
`matches/services.py::_describe_referee_divergence` использует на уровне
ОДНОГО матча) — здесь применён на уровне сезона одной команды: топ-N
матчей команды по величине расхождения. Список маленький (сезон одной
команды — обычно 20-30 матчей), гэп считается в Python, а не через SQL
`ABS()`-выражение — не оправдано ради одной сезонной секции.

**Явно задокументированное ограничение** (и в докстринге функции, и в
подписи под списком на `templates/teams/detail.html`): это разброс МНЕНИЙ
болельщиков о судействе, НЕ подтверждённый факт судейской ошибки — сайт
не может и не должен утверждать, что решение было неправильным.

### B2B v1 (`partners/services.py::build_mood_index_feed`)

Переиспользует существующую партнёрскую инфраструктуру
(`Partner.feed_token`, тот же токен-доступ, что `PartnerContentFeedView`,
ADR о которой отдельно не заводился) — новый эндпоинт
`/partners/<slug>/feed/<token>/mood/<team_id>/` отдаёт JSON с ТЕМИ ЖЕ
агрегированными числами, что уже показаны на публичной странице команды:
никаких пользовательских ID, username, IP — только числа, названия команд
и матчей. "Агрегированный вид, без раскрытия пользователей" из
продуктового запроса выполнено буквально: партнёр получает то же самое,
что видит любой посетитель страницы команды, просто в виде API вместо
HTML.

**Это НЕ полноценный B2B-продукт** — нет модели тарифов, контракта доступа
сверх уже существующего токена, отдельного рейт-лимита. Решения о том, кто
платит и сколько, кому вообще выдавать `Partner`-запись и на каких
условиях — бизнесовые, а не решаемые кодом; закрывать их сейчас означало
бы придумывать бизнес-модель без участия продукта/CEO. Код даёт РЕАЛЬНЫЙ,
работающий срез данных — ровно то, что можно сделать инженерными
средствами уже сегодня.

## Альтернативы и почему не они

- **Провести теневой прогон перед публикацией, как рекомендовал ADR-0029**
  — отклонено ПРЯМЫМ запросом пользователя после того, как альтернатива
  была явно озвучена. Задокументировано как осознанное отклонение, не
  забытый шаг — см. `docs/PRODUCT_SCOPE_MATCH_DNA_AND_EXPLAINABILITY.md`.
- **Отдельная модель `TeamMoodSnapshot` + периодическая Celery-задача**
  (первоначальный сценарий "полной версии" в scope-документе) — отклонено:
  весь необходимый ряд уже реконструируется на чтении из существующих
  `TeamMatchAggregate`/`MatchPrediction`, без исторических "срезов",
  которые бы отставали от реальных данных между прогонами задачи. Дороже
  и не даёт ничего, чего нет в текущем подходе (данные не пропадают —
  `TeamMatchAggregate` хранит все матчи, не только последние N).
- **Chart.js/Grid.js для графика** — отклонено (см. решение выше про
  SVG на сервере) — доступны как исключение для Cowork-артефактов
  (`mcp__cowork__create_artifact`), но не для рантайма самого сайта DOPX,
  где ADR-0025 уже закрыл эту дверь намеренно.

## Последствия

- `MOOD_SERIES_CACHE_TIMEOUT=3600` (тот же таймаут, что у v1
  `compute_mood_trend`) — график может отставать от самого свежего голоса
  до часа, тот же компромисс, что уже принят для бейджа.
- Систематический перекос в пользу топ-клубов (риск из ADR-0029) НЕ
  проверен экспериментально перед этим релизом — стоит вернуться к этому
  вопросу после накопления данных за фактический круг чемпионата: сверить
  `mood`/`trust` с объективной турнирной позицией на предмет корреляции,
  которая объясняется не игрой команды, а просто её популярностью/числом
  голосов.
- `build_mood_index_feed` читает `compute_mood_series`/
  `find_season_controversial_matches` напрямую — если формат этих функций
  изменится, партнёрский JSON-контракт молча изменится вместе с ним (нет
  отдельной versioned-схемы API) — приемлемо для v1 seed без внешних
  потребителей на момент написания, но при первом реальном партнёре
  стоит зафиксировать версию контракта явно.
- Тесты: `teams/tests.py` дополнен для `compute_mood_series` (заполнение
  trust/mood/expectation_pct, случай без прогнозов),
  `build_sparkline_points` (пропуски `None`, < 2 точек → пустая строка),
  `find_season_controversial_matches` (гейт по порогу, сортировка по
  убыванию); `partners/tests.py` — доступ к `PartnerMoodIndexFeedView` по
  верному/неверному токену, структура ответа без пользовательских полей.
