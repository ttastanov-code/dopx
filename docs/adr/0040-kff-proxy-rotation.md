# 0040 — Автоматическая ротация прокси при IP-блокировках

Дата: 2026-09-07
Статус: Accepted

## Контекст

Прямой запрос после ADR 0039: "наша задача сейчас — пока технически мы не
придумаем как решить вопрос интеграции или ухода на другой платный API —
избегать блокировки автоматически. Поэтому и с IP, и с другими возможными
блокировками наш парсер должен справляться" — явное расширение задачи:
раньше (ADR 0039) IP-репутация облачного хостинга (DigitalOcean/Timeweb/
Selectel, см. `docs/DEPLOYMENT.md`) была зафиксирована как единственный
слой риска, который код принципиально не может закрыть. Теперь это
требование снято — до появления платного API/прямой интеграции парсер
обязан пытаться справляться и с этим классом блокировок тоже, автоматически,
без ручного вмешательства.

Единственный технический способ автоматически обойти блокировку ПО IP —
сделать запрос с другого IP. Отсюда — пул прокси с автоматической ротацией
при обнаружении, что конкретный прокси "спалился".

## Решение

### Отдельный, не общий с глобальным circuit breaker, слой состояния

`parsers/kff/client.py`: `_proxy_pool()`, `proxy_identity()`,
`select_kff_proxy()`, `register_kff_proxy_success()`,
`register_kff_proxy_failure()`.

- `_proxy_pool()` читает `settings.PARSER_SETTINGS['PROXY_POOL']`
  (`dopx/settings.py`, env `KFF_PROXY_POOL`, формат
  `http://user:pass@host:port`, через запятую). Пуст по умолчанию.
- `select_kff_proxy()` — случайный (не round-robin — предсказуемая
  ротация сама по себе поведенческий сигнал, тот же принцип, что и джиттер
  вместо фиксированной паузы) выбор ЗДОРОВОГО прокси из пула:
  - пул пуст → `None`, поведение идентично тому, что было ДО этой фичи
    (обратная совместимость по умолчанию, вся ротация неактивна, пока
    пользователь не заполнит `KFF_PROXY_POOL`);
  - пул не пуст, но ВСЕ прокси в нём сейчас в cooldown → поднимает
    `KFFAPICircuitBreakerOpen` — то же исключение, что и у глобального
    breaker, уже корректно обрабатывается всеми вызывающими местами
    (`parsers/tasks.py::sync_kff_player_meta`, см. ADR 0038/Task #17).
- `register_kff_proxy_success/failure(proxy)` — здоровье КОНКРЕТНОГО
  прокси: 3 неудачи подряд (`_PROXY_HEALTH_THRESHOLD`) → cooldown на 20
  минут (`_PROXY_HEALTH_COOLDOWN_SECONDS`), после чего пул автоматически
  пробует его снова. Пороги НАМЕРЕННО отдельные от глобального
  `CIRCUIT_BREAKER_THRESHOLD` (5) — неудача одного прокси означает "этот
  прокси плохой", а не "нас забанили целиком", поэтому порог ниже и
  реакция мягче (не останавливает весь парсинг, просто исключает один
  IP из ротации).
- `proxy_identity(proxy_url)` — sha256-хэш URL прокси (12 символов) для
  cache-ключей и логов, чтобы логин:пароль прокси-сервиса никогда не попал
  ни в Redis-ключи, ни в логи при ошибках.

### Cookies разделены по identity прокси

`load_kff_cookies`/`save_kff_cookies` (уже существовали, ADR 0039) теперь
принимают `identity` — `None` при прямом подключении (тот же плоский ключ,
что раньше), хэш прокси при активном пуле. Разные прокси = разные видимые
Cloudflare IP = не должны делить один cookie jar — иначе сама смена IP
внутри одной "сессии" с теми же cookies стала бы подозрительным сигналом,
а не решением проблемы.

### KFFClient (JSON API)

`KFFClient.__init__` больше не грузит cookies сразу — вместо этого
`_resolve_identity()` вызывается лениво, из `_get()` (единственное место,
всегда обёрнутое в try/except у всех вызывающих): выбирает прокси,
применяет к `self.session.proxies`, грузит cookies под нужным identity.
Отложено намеренно — `KFFClient()` создаётся во многих местах ВНЕ
try/except (например, `sync_kff_premier_league`), а `select_kff_proxy()`
может поднять `KFFAPICircuitBreakerOpen`.

### photo_scraper.py (HTML-скрапинг, Task #24 этой сессии)

`_session()` — теперь единственный choke point и для этого модуля:
вызывает `select_kff_proxy()`, применяет прокси к сессии (curl_cffi через
параметр `proxy=`, requests через `session.proxies`), грузит cookies под
нужным identity, возвращает `(session, proxy)` вместо просто `session`.
`_fetch_html(session, url, proxy=None)` и `download_photo_bytes()` приняли
`proxy` и вызывают `register_kff_proxy_success/failure(proxy)` рядом с уже
существующими `register_kff_success/failure()`, и передают identity в
`save_kff_cookies`. Все три вызывающих места (`scrape_team_list`,
`scrape_team_squad`, `download_photo_bytes`) распаковывают
`session, proxy = _session()` и пробрасывают `proxy` в `_fetch_html`.

## Альтернативы и почему не они

- **Round-robin вместо случайного выбора** — отклонено: идеально
  предсказуемый порядок смены IP сам по себе поведенческий сигнал для
  anti-bot скоринга, та же логика, что джиттер вместо фиксированной паузы
  везде в этом модуле.
- **Общий с глобальным circuit breaker счётчик/порог** — отклонено:
  смешало бы два разных по смыслу сигнала ("этот прокси плохой" vs "нас
  банят совсем"), увеличило бы риск случайно сломать уже проверенный,
  покрытый тестами и интегрированный в дашборд глобальный breaker.
- **Round-robin/явный выбор прокси на уровне вызывающего кода
  (parsers/tasks.py)** — отклонено: расползлось бы знание о прокси-пуле
  по всему кодбейзу; `select_kff_proxy()`/`_resolve_identity()` держат это
  целиком внутри client.py/photo_scraper.py, вызывающий код как раньше
  просто ловит `KFFAPICircuitBreakerOpen`.

## Источник прокси — НЕ решено этим ADR

Эта фича — только инфраструктура: пока `KFF_PROXY_POOL` пуст (по
умолчанию), поведение на 100% идентично тому, что было до этого ADR.
Откуда брать реальные IP прокси (коммерческий residential/rotating-прокси
сервис, самостоятельно поднятые VPS-релеи как дешёвая альтернатива, или
явный whitelist от KFF, раз устное разрешение уже есть) — отдельное
решение пользователя (стоимость/вендор), не техническая часть, которую
можно решить в одностороннем порядке.

## Последствия

- До заполнения `KFF_PROXY_POOL` — нулевое изменение поведения
  (`select_kff_proxy()` всегда `None`), проверено юнит-тестом.
- После заполнения — парсер автоматически исключает "спалившийся" прокси
  из ротации на 20 минут и переключается на следующий здоровый, не
  требуя ручного вмешательства; если весь пул исчерпан — явно
  останавливается (`KFFAPICircuitBreakerOpen`), как и раньше при обычном
  circuit breaker, а не продолжает биться в стену.
- Верификация: `py_compile` всех тронутых файлов (`client.py`,
  `photo_scraper.py`, `dopx/settings.py`) — чисто. Отдельный юнит-тест
  (`importlib`, застабленные `django.conf.settings`/`django.core.cache.cache`)
  прогнал 7 сценариев на РЕАЛЬНОМ `client.py`: пустой пул → `None`; оба
  прокси здоровы → выбор только среди них; 3 подряд неудачи одного прокси
  → он исключается, выбирается только другой; `register_kff_proxy_success`
  сбрасывает счётчик неудач; весь пул в cooldown → `KFFAPICircuitBreakerOpen`;
  `proxy=None` для success/failure — безопасный no-op; 2/3 неудачи (ниже
  порога) — прокси остаётся в ротации. Все 7 — OK.
