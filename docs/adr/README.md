# Architecture Decision Records (ADR)

Здесь фиксируются архитектурные и продуктовые решения проекта — не то
"как написан код" (это видно и так), а то, **почему** он написан именно
так, какие альтернативы рассматривались и от чего сознательно отказались.

## Почему это появилось (2026-09-04)

До этого момента "память" проекта жила прямо в коде — длинными
комментариями вида "БАГ, КОТОРЫЙ ТУТ БЫЛ" или "ПОЧЕМУ ЭТО ЗДЕСЬ". Это
работало для соло-разработки, но не масштабируется на команду: комментарий
разрастается на 20-30 строк внутри функции, затрудняет чтение самого кода,
и его невозможно найти, если не знаешь, в каком файле искать. Плюс это
выглядит и читается как код, написанный ИИ — что не добавляет доверия при
показе кода сторонним разработчикам.

Новое правило: если решение достаточно важное, чтобы объяснять его на
20+ строк — оно достаточно важное для отдельного ADR-файла. В коде рядом с
местом, которого касается решение, остаётся короткая ссылка вида
`# см. docs/adr/0007-...md` и одно предложение сути (что нельзя делать и
почему), а не полная предыстория.

## Формат

Файл: `docs/adr/NNNN-короткое-название.md`, где `NNNN` — следующий по
порядку четырёхзначный номер (не переиспользуется, даже если решение потом
отменено — см. статус `Superseded`).

```markdown
# NNNN — Заголовок решения

Дата: YYYY-MM-DD
Статус: Accepted | Superseded by NNNN | Deprecated

## Контекст
Какая проблема была, что происходило без этого решения (конкретный баг/
инцидент/риск, если есть — со ссылкой на файл и строку).

## Решение
Что именно сделали.

## Альтернативы и почему не они
Что рассматривали, почему отклонили.

## Последствия
Что это меняет для кода/процесса, на что стоит обратить внимание в будущем.
```

## Когда писать ADR, а когда — оставить обычный комментарий

- Обычный комментарий (1-5 строк, прямо в коде): "почему эта строка
  написана не очевидным способом" — например, обход конкретной особенности
  библиотеки, порядок операций для избежания race condition.
- ADR: решение затрагивает несколько файлов/приложений, меняет процесс
  (деплой, CI), вводит новый паттерн, который дальше должен повторяться в
  проекте, или было принято после реального инцидента, который стоит помнить
  не только автору правки.
