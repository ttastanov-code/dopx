# 0041 — Обработка "техническое поражение" (technical_defeat) от KFF

Дата: 2026-09-08
Статус: Accepted

## Контекст

Пользователь показал матч #1046 (Алтай Өскемен — Кызылжар, 8 авг 2026,
21-й тур КПЛ): на kffleague.kz результат давно известен (3:0, баннер
«Матчу засчитано техническое поражение»), а на DOPX матч навсегда завис
в статусе «Запланирован». Заодно показал ещё три матча (25-й тур, 6 сент
2026) — те у KFF обычные `status="finished"`, а на DOPX всё ещё
«Запланирован».

Прямой запрос к API (`/api/v1/games/1046?...`) подтвердил: KFF отдаёт
`"status":"technical_defeat"`, `"is_technical":true`, при этом
`home_score`/`away_score` уже проставлены (3:0) — счёт есть, просто наш
статус не опознан. Полный список сырых статусов в сезоне 200 (240
матчей): `upcoming` (51), `finished` (188), `technical_defeat` (1) — то
есть единичный, но реальный случай, не гипотетический.

## Найденные баги (2 независимых места, один класс проблемы)

1. **`parsers/kff/importers.py::STATUS_MAP`** — не содержал ключ
   `"technical_defeat"`. `import_match_core` через
   `STATUS_MAP.get(raw_status, "scheduled")` и `update_match_statuses`
   (`parsers/tasks.py`) через `STATUS_MAP.get(api_status, match.status)`
   оба молча проваливались в дефолт (соответственно "scheduled" или
   "без изменений") вместо ошибки — из-за этого баг мог существовать
   месяц незамеченным: НИ ОДИН прогон не оставил следа в логах.
2. **`parsers/kff/client.py::get_recent_finished_matches`** — фильтр
   `finished = [m for m in all_matches if m.get('status') == 'finished']`
   тоже не признавал `technical_defeat` "завершённым", поэтому матч
   никогда не попадал в выборку "последних N завершённых" для
   `sync_recent_matches` (Celery Beat, каждые 30 мин) — единственного
   пути, которым НОВЫЙ (ещё не существующий локально) матч вообще
   попадает в базу впервые с уже финальным результатом.

## Решение

- `STATUS_MAP["technical_defeat"] = "finished"`, `STATUS_MAP[
  "technical_win"] = "finished"` (второе — защитно, симметричный исход,
  не встречался в реальных данных, но по той же причине не должен
  провалиться в дефолт, если KFF когда-нибудь пришлёт его).
- `get_recent_finished_matches`: множество "статусов, похожих на
  завершённый" расширено с `{"finished"}` до `{"finished",
  "technical_defeat", "technical_win"}`.
- **Защитное логирование** (новое, не было раньше ни в одном из двух
  мест): любой raw-статус KFF, которого нет в `STATUS_MAP`, теперь пишет
  `logger.warning` с явным текстом "нужно добавить в STATUS_MAP" — и в
  `import_match_core`, и в `update_match_statuses`. Раньше оба места
  проваливались в безопасный, но абсолютно тихий дефолт — именно поэтому
  этот класс бага не был замечен ни разу за месяц. Теперь следующий
  новый статус (если KFF когда-нибудь его введёт) будет виден в логах
  сразу же, а не только когда пользователь заметит зависший матч вручную.

## Почему остальные 3 матча (обычный `finished`) тоже зависли

Прямой запрос к `/api/v1/seasons/200/games` подтвердил: у KFF эти три
матча (id 1078/1079/1083, 25-й тур, 6 сент 2026) уже давно
`status="finished"` с проставленным счётом — то есть с точки зрения
данных и кода никакого бага для НИХ нет, `STATUS_MAP["finished"] =
"finished"` и так работал верно. Это означает, что синхронизирующие
задачи (`sync-kff-recent-premier` каждые 30 мин, `update-live-matches`/
`update-upcoming-matches-full` через `update_match_statuses`) либо не
выполнялись физически (Celery beat/worker не запущены в этом локальном
dev-окружении), либо упирались в circuit breaker/cooldown в тот период.
Это не код-баг, а вопрос "выполняется ли воркер прямо сейчас" — не
проверяемый из этой сессии (процессы Celery работают на компьютере
пользователя, не в песочнице, где выполняется этот код). Для немедленного
разбора backlog есть готовая management-команда `python manage.py
sync_kff` — она делает полную синхронизацию без Celery.

## Верификация

- `py_compile` всех трёх изменённых файлов (`importers.py`, `client.py`,
  `tasks.py`) — чисто.
- Прямой запрос к живому `kffleague.kz/api/v1/...` подтвердил точный
  сырой JSON для матча #1046 (technical_defeat, home_score=3,
  away_score=0) и для 1078/1079/1083 (finished) — исправление направлено
  именно на то расхождение, что реально пришло от KFF, не на
  гипотетическую структуру.
- Полный список статусов в сезоне (240 матчей, способ — прямой
  JS-запрос к `/api/v1/seasons/200/games` через браузер) подтвердил, что
  `technical_defeat` — единственный незамапленный статус в текущих
  данных; `technical_win` добавлен защитно без реального прецедента.

## Дальнейшее (не сделано в этом ADR, на усмотрение пользователя)

KFF показывает отдельный баннер "Техническая победа/поражение" —
у нас после этого фикса матч просто корректно станет "Завершён" с верным
счётом, БЕЗ отдельной пометки "техническое поражение" на странице матча
(это потребовало бы нового поля в `Match`, миграции и изменений в
шаблоне — отдельная, более крупная задача, если понадобится паритет с
UI самого KFF).
