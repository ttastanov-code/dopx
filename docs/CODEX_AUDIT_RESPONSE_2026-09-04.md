## 1. Что проверено и подтверждено как реальная проблема

### P0 — Целостность оценок через API (СОГЛАСЕН, критично)

Проверено лично построчно: `api/serializers.py` (все 6 сериалайзеров оценок)
и `evaluations/forms.py`.

Факт: веб-форма физически не даёт подсунуть чужую сущность — `queryset`
`supported_team` ограничен двумя командами матча (`forms.py:44-46`), поля
игроков генерируются ТОЛЬКО из реального состава через
`MatchLineupPlayer.objects.filter(lineup__match=self.match)` (`forms.py:175-177`),
поля тренеров — только из `match.home_coach`/`match.away_coach`
(`forms.py:253`). Подделать чужого игрока через веб физически негде — в
форме просто нет такого поля.

API — прямая противоположность. Все шесть `validate()` в
`api/serializers.py` проверяют ТОЛЬКО: (1) окно голосования открыто,
(2) юзер ещё не голосовал за эту пару (уникальность), (3) контекст
просмотра создан. Ни один не проверяет, что `player` реально играл в этом
`match`, что `team`/`coach` реально участвовали, что `supported_team` —
одна из двух команд матча. `PlayerEvaluationSerializer`, например, примет
`{"match": <id>, "player": <любой id из другого матча>, "contribution": 10}`
от любого верифицированного пользователя (`api/views.py:123-124`:
`IsAuthenticatedAndVerified` + `VotingOpenPermission` — верификация есть,
принадлежность сущности матчу — нет).

Это не теоретический риск. Верификация email не требует ничего, кроме
рабочей почты — конкурирующий фанат одной команды может систематически
занижать рейтинг чужого игрока или накручивать своего через прямые POST
без единой строчки взлома, просто зная структуру API (она в `drf-spectacular`
публично документирована). Аггрегаты, тур/сезонная сборная — всё считается
из этих же таблиц.

**План.** Единый `EvaluationPolicy` (или набор `clean_*`/`validate()`
проверок в сериалайзерах, если не хотим сейчас городить сервисный слой) с
пятью правилами из ревью: матч завершён + окно открыто, контекст создан,
команда — домашняя/гостевая, игрок — в заявке матча, тренер/судья —
назначены на матч. Плюс тест-кейсы на каждую попытку "оценить чужого".

Не считаю нужным сразу заворачивать это в отдельный `core/policies.py` для
ВСЕГО проекта, как предлагает Codex (слой `selectors/services/policies` на
весь бизнес) — это правильное направление, но за один заход это большой
рефакторинг с риском что-то сломать при отсутствии Django в песочнице для
реального прогона тестов. Предлагаю: сделать `EvaluationPolicy` узко под
эту дыру, вызывать его и из forms.py, и из serializers.py (единая точка
правды, дублирование правил исчезает само), остальной домен — не трогать,
пока не появится вторая похожая дыра, которая оправдает более широкий
рефакторинг.

### Дополнительная находка (её нет в ревью Codex, но она серьёзнее по объёму данных)

Все ползунки (`type="range"`) во всех формах оценки стоят на `initial=5`
и физически всегда шлют значение в POST — html range-input не может быть
"пустым". Ни в `evaluations/forms.py`, ни во views нет отслеживания
"пользователь реально подвинул ползунок". Значит уже сейчас, скорее всего,
часть базы — это не осознанные "5 из 10", а дефолт от пользователей,
кликнувших "Далее" не глядя. Это ровно то, о чём предупреждает сам Codex
("не показывать 8.7 против 8.6 без учёта выборки") — только на шаг раньше:
проблема не только в размере выборки, но и в том, что часть голосов внутри
выборки может быть шумом, а не мнением. Стоит чинить одновременно с
UX-редизайном шага оценки игроков (см. раздел 4) — там всё равно меняем
разметку ползунков.

### CI/CD — pip-audit и check --deploy (СОГЛАСЕН по фактам)

Проверено: `.github/workflows/deploy.yml:116-126` — `pip-audit` действительно
`continue-on-error: true`, с честным комментарием "первый прогон нужно
разобрать вручную". `docs/DEPLOYMENT.md:299-306` действительно утверждает,
что CI гоняет `manage.py check --deploy` — в реальном workflow этого шага
нет (`.github/workflows/deploy.yml:104-114`, только `manage.py check` без
`--deploy`).

**План.** Добавить шаг `python manage.py check --deploy` в `test`-job (это
не блокирует деплой сейчас — сервер ещё не подключён, но должно попадать в
лог CI, чтобы предупреждения были видны при каждом пуше, а не потеряны в
формулировке доки). Про `pip-audit`: сначала разобрать текущую выдачу
руками (это разовая задача на 20 минут), затем снять `continue-on-error`.

### Бэкапы — только ручные (СОГЛАСЕН, но это продакшен-задача)

Подтверждено: `docs/DEPLOYMENT.md:194-203` описывает только ручной
`pg_dump`/восстановление. Реального сервера ещё нет (см. комментарий в
`deploy.yml:15-20` — секреты деплоя не заданы), поэтому автоматизировать
бэкапы буквально некуда — это работа, привязанная к моменту появления
прод-сервера. Кладу в корзину "готовим план, не делаем" ниже.

### Миграции на старте web-контейнера (СОГЛАСЕН с направлением, не срочно)

Подтверждено: `docker/entrypoint.sh:44-47` — `migrate --noinput` при каждом
старте `gunicorn`-контейнера, без разделения на отдельный deploy-job. На
нынешнем масштабе (один сервер, ручной SSH-деплой) это осознанный и
задокументированный компромисс, не баг. Пересматривать стоит, когда
появится вопрос "как деплоить без даунтайма" — то есть тоже продакшен-этап.

### Виджеты — `frame-ancestors *` (СОГЛАСЕН с фактом, НЕ считаю срочным)

Подтверждено: `dopx/middleware.py` осознанно ставит `frame-ancestors *`
именно и только на пути виджетов (`WIDGET_PATH_PATTERN`), весь остальной
сайт — `frame-ancestors 'self'` + `X_FRAME_OPTIONS = 'DENY'`
(`dopx/settings.py:549`). Это архитектурно чистое решение, а не дыра "по
всему сайту". Ограничивать доменным allow-list есть смысл, когда появятся
первые реальные партнёры (сейчас его физически некому обходить во вред —
эмбед никому не выдан). Тоже в корзину "готовим", не "делаем".

### Viewport — `user-scalable=no` (СОГЛАСЕН, тривиальный фикс)

Подтверждено: `templates/base.html:8` —
`maximum-scale=1.0, user-scalable=no`. Это реальное нарушение WCAG 2.1 SC
1.4.4 (запрет масштабирования жестом), бьёт по людям со слабым зрением
прямо сейчас, не в продакшене. Правки на одну строку, нулевой риск. Сделаю
сразу по согласованию (см. план ниже), это не требует обсуждения.

## 2. С чем согласен частично или не согласен

**Слой `selectors/services/policies` на весь проект.** Направление верное
(дублирование правил между `forms.py`/`serializers.py`/`views.py`/`tasks.py`
реально есть и реально ровно поэтому появилась дыра из P0), но делать это
одним большим рефакторингом сейчас — риск выше пользы: в песочнице нет
доступа к запущенному Django, полноценный прогон тестов после большого
рефакторинга здесь недоступен, а из чата без реальной БД трудно
гарантировать отсутствие регресса на 6-шаговом визарде оценки. Предлагаю
делать это точечно, по мере повторения проблемы, а не как отдельный
крупный спринт "архитектура ради архитектуры".

**Перенос исторических комментариев в ADR.** Не согласен с приоритетом
(не с идеей — она разумна для команды из нескольких разработчиков). Сейчас
DOPX — соло-проект без отдельной вики, и длинные комментарии в коде — это
единственная работающая память проекта: они уже не раз спасали от повторения
одной и той же ошибки (в файлах видно прямые ссылки "БАГ, КОТОРЫЙ ТУТ БЫЛ").
Переносить их в отдельные ADR-файлы добавляет косвенность без реального
выигрыша, пока нет второго разработчика, который бы их читал отдельно от
кода. Возвращаться к этому имеет смысл, когда в команде появится второй
человек.

**Парсинг KFF / план Б.** Согласен с диагнозом, но это уже решённый вопрос
с нашей стороны — переход на платный Stratorium запланирован. Единственное,
что предлагаю добавить дёшево и уже сейчас (не дожидаясь миграции): лёгкий
журнал расхождений при импорте (сколько строк разошлось с предыдущим
состоянием, флаг на ручную проверку) — это несколько часов работы и снижает
риск тихого искажения агрегатов, пока мы всё ещё на бесплатном парсинге.

**CDN-зависимости, сборка Tailwind, SSE/WebSocket.** Согласен по существу,
но это явно продакшен-этап оптимизации, а не задача текущего цикла — беру
в корзину "готовим план", как вы и сказали.

6. **UX быстрой оценки** — см. раздел 4 ниже, встроено в существующий визард.

### Корзина Б — готовим (документ/дизайн, не внедряем до продакшена)

Ничего из этого не трогаем руками сейчас, только фиксируем план на будущее:

- Уход от CDN/Tailwind browser runtime → сборка на этапе build.
- Автоматический зашифрованный офсайт-бэкап Postgres + media, с
  ежемесячной проверкой восстановления.
- Отдельный deploy-job `migrate → smoke test → rolling restart` вместо

- SSE/WebSocket для live-страниц вместо polling.

### Корзина В — бэклог идей (после того как закрыта корзина А)

- Explainability рейтингов: показывать число оценок и пометку

## 4. UX быстрой оценки — без отдельного функционала

Требование: не параллельная фича, а часть текущего визарда — пользователь
должен мочь оценить быстро ИЛИ вдумчиво и полностью, оставаясь в одном и
том же потоке `Context → Teams → Players → Coaches → Referee → Match final`.

Механика:

1. **Выбор режима — не отдельный экран, а переключатель на шаге 1
   (контекст).** Два больших таба сверху формы контекста: "Быстро — 1
   минута" / "Подробно — полный разбор". Выбор пишется в
   `EvaluationSession` (там уже есть `completed_steps`/`current_step`,
   добавить поле `mode`). Никакого нового флоу — те же 6 шагов, тот же URL,
   тот же прогресс-бар.

2. **Шаг "Игроки" — самый тяжёлый, здесь разница ощутимее всего.**
   Сейчас форма уже технически не требует оценивать весь состав (каждый
   игрок — чекбокс `evaluate` + три диапазона, задизейбленных пока чекбокс
   не включён — `evaluations/forms.py:184-192`), проблема чисто в
   интерфейсе: пользователь видит сразу всех 20+ игроков и теряется.
   В режиме "Быстро": наверху блок из 3-5 карточек стартового состава
   (капитан + игроки с наибольшим числом минут/событий, если событие матча
   уже спарсено — иначе просто первые по номеру из стартового состава),
   чекбоксы у них уже включены — можно сразу крутить ползунки и идти
   дальше. Остальной состав — под разворачивающимся "Показать весь состав
   (X игроков)", без принудительного скролла. В режиме "Подробно" — сразу
   открыт весь список, как сейчас.

3. **Шаг "Тренеры"/"Судья" в быстром режиме** — вместо 4 отдельных
   ползунков на тренера/2 на судью один общий вопрос с 3 крупными кнопками
   вместо шкалы ("Слабо" / "Нормально" / "Сильно"), который на бэкенде
   мапится в те же самые поля модели (например "Сильно" → все под-метрики
   на 8). Модель и `CoachEvaluationForm`/`RefereeEvaluationForm` не меняются
   — меняется только то, какой виджет их рендерит и что подставляется по
   умолчанию при клике. В "Подробно" — как сейчас, все шкалы отдельно.

4. **Анти-шум одновременно с этим редизайном.** Раз уж переделываем
   разметку ползунков — добавляем `data-touched="false"` на каждый `range`,
   JS слушает первый `input`-эвент и переключает в `true`, значение
   отправляется в скрытом сопутствующем поле. `PlayerEvaluationForm` и
   остальные формы игнорируют критерий, если `touched=false` (в "Быстро" —
   это неважно для предвыбранных 3-5 карточек, они по умолчанию должны
   считаться "тронутыми", раз пользователь явно их выбрал через чекбокс).

5. **После отправки — сразу отдача, которую просит Codex** (и это дёшево
   реализовать, все данные уже считаются в `aggregates`): на экране
   "Спасибо" — "Вы вошли в N оценок этого матча", и если у игрока уже есть
   предыдущий агрегат с рангом — "поднялся/опустился на K позиций в
   рейтинге тура". Не требует новых моделей — читаем `PlayerMatchAggregate`
   до и после сохранения оценки в рамках того же запроса.

Итог: один визард, один набор URL и моделей, разница только в том, что
показано на экране и что предзаполнено — то есть ровно то, что вы просили:
без отдельного параллельного функционала.
