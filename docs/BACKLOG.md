## [ЧАСТИЧНО РЕШЕНО 2026-08-21] KFF публикует перенос раньше, чем меняет status/date в API

Зафиксировано: 2026-08-21, живой пример — матч Окжетпес–Кызылжар (KFF
external_id=1066). Пользователь сделал полный ресинк сезона — матч на сайте
DOPX остался "Запланирован" со старой датой. Проверка на самом kff.kz
(https://kffleague.kz/ru/matches/1066) показала: у KFF ТОЖЕ дата и время
матча всё ещё старые ("сб, 22 авг. 2026 г. 17:00"), меняется только
отдельный текстовый баннер под счётом: "Дата и время проведения данного
матча перенесены на неопределенный срок."

Вывод: `update_match_statuses` (parsers/tasks.py) читает `game_data.get("status")`
и `game_data.get("date")` из `/api/v1/games/{id}` — судя по тому, что на
самой странице матча дата тоже не изменилась, эти поля у KFF, скорее всего,
ещё не тронуты, баннер — что-то отдельное. Не удалось окончательно
проверить сырой JSON (в этой рабочей среде нет сетевого доступа к API KFF с
нужными заголовками — только к обычным HTML-страницам). **Нужно от
пользователя:** зайти в `/staff/dashboard/parser/`, ввести external_id=1066,
эндпоинт "Детали матча" ("game"), и посмотреть сырой ответ — если там
обнаружится поле вроде `notice`/`info`/`is_postponed`, которое мы сейчас не
читаем, можно будет ловить перенос ещё до того, как KFF поменяет
структурные `status`/`date`.

**Сделано независимо от результата проверки:** обнаружен и закрыт
сопутствующий баг — если бы staff вручную поставил матчу `status='postponed'`
в админке ДО того, как KFF обновит свои данные, `update_match_statuses` на
следующем же цикле (10-15 минут) тихо откатил бы это обратно в "scheduled"
(`STATUS_MAP.get(api_status)` всегда пересчитывает статус заново из ответа
KFF, ручные правки ничем не защищены). Добавлено поле `Match.manual_override`
(`matches/migrations/0004_match_manual_override.py`) — пока `True`,
`update_match_statuses` пропускает статус/дату этого матча целиком (даже не
дёргает API). В `MatchAdmin` (matches/admin.py) — два action'а: "Пометить
перенесённым вручную" (ставит `status='postponed'` + `manual_override=True`
разом) и "Снять ручную пометку" (когда KFF наконец опубликует настоящую
новую дату). Итог: сейчас у staff есть немедленный рабочий инструмент для
этого конкретного матча, независимо от того, найдётся ли в API
дополнительный сигнал.

## Мультисезонность/мультилиговость: баг главной таблицы + формат "кубок" + фильтрация списков по сезону

Зафиксировано: 2026-08-17, дополнено 2026-08-18. Находки 1 и 3 (включая
структурный слой историзации — только для игроков) выполнены 2026-08-21 по
явной команде пользователя. Находка 2 (формат "кубок") остаётся ОТЛОЖЕНА —
реальные данные Кубка Казахстана пока не планируется грузить в БД, это
risk-awareness запись, а не задача в работу.

### Находка 1 — [РЕШЕНО 2026-08-21] баг (сработал бы, как только появится 2-я активная лига)

Было: `core/views.py::standings_preview` брал `Season.objects.filter(is_active=True).first()`
БЕЗ фильтра по лиге — с одной активной лигой работало случайно правильно,
но как только у второй лиги появился бы свой активный сезон, какая таблица
попадёт на главную решала бы сортировка `Season.Meta.ordering = ['-year']`,
а не осмысленный выбор.

Сделано: добавлен `League.is_primary` (BooleanField с тем же
singleton-паттерном в `save()`, что и `Season.is_active`) — миграция
`leagues/migrations/0002_league_is_primary.py` (AddField + data-миграция,
автоматически помечает главной лигу текущего активного сезона, если он
есть, иначе первую лигу по алфавиту). Добавлен `Season.get_primary_active()`
(seasons/models.py) — единая точка правды "какой сезон сейчас показываем по
умолчанию" (активный сезон главной лиги, с fallback на старое поведение,
если `is_primary` ещё не проставлен). `standings_preview` и все списки из
находки 3 используют именно его.

### Находка 2 — архитектурный пробел: нет понятия "формат соревнования"

Ни `League`, ни `Match` не знают о существовании кубкового (на выбывание)
формата — только круговая таблица. Если завести Кубок Казахстана как
обычную `League` с активным сезоном, движок молча посчитает и покажет
бессмысленную W-D-L/очки таблицу (aggregates/tasks.py::recalculate_season_standings
жёстко предполагает круговой турнир). Нужно перед загрузкой реальных
данных кубка:
1. Поле формата на `League` (`format`: `league`/`cup` или `is_cup`
   BooleanField).
2. Поле раунда/стадии на `Match` (`round`/`stage`: групповой этап, 1/8,
   1/4, 1/2, финал, + возможно `leg` для двух матчей туда-обратно).
3. `standings_preview`/`recalculate_season_standings` должны пропускать
   лиги с `format='cup'` — им нужен отдельный виджет (сетка плей-офф), не
   таблица. Отдельная фронтенд-задача, не переиспользует текущий UI
   таблицы.

Не блокирует ничего прямо сейчас — просто предупреждение "не заводите
Кубок как обычную лигу в проде, пока это не сделано".

### Находка 3 — [РЕШЕНО 2026-08-21, быстрый слой] списки teams/players/coaches не фильтровались по сезону

Зафиксировано: 2026-08-18, по вопросу пользователя "что будет на этих
страницах, когда начнётся следующий сезон КПЛ". Проверено (на момент
обнаружения):

- `Season.save()` устроена правильно — при сохранении сезона с
  `is_active=True` все остальные сезоны ЭТОЙ лиги автоматически гасятся,
  так что "текущий сезон лиги" всегда однозначен.
- `TeamSeason` корректно пишется при каждом импорте матча — связь
  команда↔сезон в БД есть, ей просто никто не пользуется на списках.
- Но `TeamListView`/`PlayerListView`/`CoachListView`/`RefereeListView`
  (teams/players/coaches/referees `views.py`) вообще не фильтруют по
  сезону/лиге — `Team.objects.all()` и т.д. показывают ВСЁ, что когда-либо
  импортировано, одним списком навсегда.
- `is_active` у Player/Coach/Referee нигде программно не гасится (только
  выставляется в True при создании/реактивации) — сейчас декоративное
  поле, не сигнал "участвует в текущем сезоне".
- `Player.team`/`Coach.team` — одиночный FK "текущая команда", а не
  история по сезонам. При трансфере/смене сезона старая привязка просто
  перезатирается; carrier-история сохраняется только на уровне состава
  конкретного матча (`MatchLineupPlayer`), нигде не показывается как
  "карьера".

Итог: когда сезон закончится и начнётся следующий, вылетевшие команды и
ушедшие игроки/тренеры НЕ пропадут (это ожидаемо и не должно быть
починено удалением), но и никак не отделятся от текущего состава —
будут висеть в тех же общих списках навсегда вперемешку с актуальными.

**Сделано (быстрый слой, 2026-08-21):**

`TeamListView`/`PlayerListView`/`CoachListView` (teams/players/coaches
`views.py`) теперь по умолчанию фильтруют по `Season.get_primary_active()`
через `TeamSeason` (для players/coaches — по текущей команде игрока/тренера,
`team__teamseason__season=...`, а не по факту участия в конкретных матчах
сезона — проще и достаточно для цели "не мешать актуальный состав с
историческим"). Добавлен переключатель `?season=all` (компонент
`templates/components/_season_scope_toggle.html`, тег `query_transform` в
`core/templatetags/querystring_extras.py` сохраняет остальные GET-параметры
при переключении/пагинации). `RefereeListView` НЕ сезонится — явное решение
пользователя (судьи не привязаны к команде, список остаётся глобальным).

**Сделано (структурный слой — только для игроков, 2026-08-21):**

Полноценная историзация через новую модель (`PlayerSeason`/`CoachSeason` по
аналогии с `TeamSeason`) НЕ потребовалась — команда-по-сезонам для игрока
восстанавливается прямым запросом к уже существующему `MatchLineupPlayer`
(каждая запись состава жёстко привязана к факту участия в конкретном матче
конкретного сезона через `lineup.team`/`lineup.match.season`, задним числом
не переписывается — в отличие от `Player.team`, который хранит только
ТЕКУЩУЮ команду). `PlayerDetailView.get_context_data` (players/views.py)
группирует записи по (сезон, команда) в Python — если игрок менял клуб в
разгар сезона, получает две отдельные строки за один год, это корректное
отображение, не баг. Голы на отрезок сезон+команда — через `MatchEvent`,
дополнительным запросом по id матчей отрезка. Блок "По сезонам" —
`templates/players/detail.html`, между "Историей выступлений" и "Лучшими
матчами".

Для тренеров та же историзация СТРУКТУРНО НЕВОЗМОЖНА (см. находку 4 ниже):
KFF не хранит историю назначений тренеров вообще, ни в одном матче, ни в
каком-либо виде источника — заполнить `CoachSeason`/аналогичный запрос было
бы физически нечем. Осознанно не делается, не техдолг.

### Находка 4 — [РЕШЕНО 2026-08-18] статистика тренера не разделялась по "при каком тренере сыгран матч"

Зафиксировано: 2026-08-18, по живому примеру пользователя: тренер Самат
Смаков пришёл в «Атырау» и провёл как тренер 2 матча, но на сайте у него
показано 21 (= почти весь сезон клуба).

Гипотеза о собственном баге (нестрогий guard в `import_coaches`,
позволявший `sync_recent_matches` переписывать `home_coach`/`away_coach`
задним числом при каждом периодическом ресинке) НЕ подтвердилась как
основная причина. Проверка через `resync_finished_match_coaches --team
Атырау --dry-run` (реальные запросы к KFF `/lineup` по каждому
завершённому матчу) показала: 0 изменений из 21 матча — то есть KFF
СЕГОДНЯ отдаёт текущего тренера даже для матчей трёхмесячной давности.
Пользователь подтвердил вручную на сайте kff.kz: при смене тренера клуба
KFF просто отвязывает старого и привязывает нового — история назначений
не хранится вообще, ни в конкретном матче, ни где-либо ещё в их системе.
Итог: это ограничение источника данных, а не решаемый баг импорта —
"кто вёл конкретный исторический матч" физически не восстановить.

**Что сделано вместо починки данных (раз данных для починки не существует):**

1. `parsers/kff/importers.py::import_coaches` — guard всё равно оставлен
   (не даёт `home_coach`/`away_coach` меняться у уже `finished` матча):
   не чинит историю, но хотя бы не даёт ей "плыть" туда-сюда при каждом
   ресинке одного и того же (заведомо неточного) значения.
2. `coaches/views.py`/`templates/coaches/list.html`/`detail.html` —
   счётчик "Матчей" убран целиком (был системно недостоверен), заменён на
   "Оценок" (`evaluations_count`/`total_evaluations` через
   `CoachEvaluation` — эта привязка НЕ страдает той же проблемой: болельщик
   оценивает конкретного тренера вскоре после матча, эта запись не
   переписывается задним числом при смене тренерского штаба).
3. Блок "Последние матчи" на странице тренера переименован в "Форма
   команды" — те же данные (последние матчи текущего клуба тренера), но
   честно подписаны как командные, с явным пояснением под заголовком, а
   не выданы за персональную статистику тренера.
4. `resync_finished_match_coaches` (core/management/commands/) оставлена
   в проекте — рабочий инструмент диагностики на будущее (например, если
   KFF когда-нибудь начнёт отдавать историю, или для разовой проверки
   конкретной команды/тренера).

**Не проверено и не тронуто:** аналогичный риск для `Player.team`
(`parsers/kff/importers.py::get_or_create_player` тоже перезаписывает
команду при каждом импорте состава) — НО фактическая статистика "матчей"
игрока считается через `MatchLineupPlayer` (реальное историческое участие
в конкретном составе конкретного матча), а не через текущий `Player.team`
— в отличие от тренеров, эта привязка иммутабельна и не подвержена той
же проблеме. Отдельно проверять не требуется, но если появится жалоба на
статистику игроков — начать отсюда.

## [ОТЛОЖЕНО] Alpine.js → CSP-safe сборка (@alpinejs/csp)

Зафиксировано: 2026-08-17. Отложено из-за недельного лимита (94% использовано
на момент решения) — риск не успеть атомарно завершить рефакторинг и оставить
CSP в переходном ломающемся состоянии. Начать в след. сессии со свежим лимитом.

### Суть

Сейчас `dopx/middleware.py::ContentSecurityPolicyMiddleware` держит
`'unsafe-eval'` и `'unsafe-inline'` в `script-src`, потому что Alpine.js по
всем шаблонам используется в inline-форме (`x-data="{...}"`,
`x-show="..."`, `@click="..."` прямо в HTML-атрибутах) — Alpine компилирует
эти выражения через `new AsyncFunction(...)`, что CSP трактует как eval.

Цель: перейти на `@alpinejs/csp` — сборку Alpine, которая ЗАПРЕЩАЕТ inline
x-data-выражения и требует регистрировать компоненты через `Alpine.data(...)`
в обычном JS-файле. После этого `'unsafe-eval'` (и в идеале `'unsafe-inline'`
для script-src, через nonce/hash) можно убрать из CSP полностью.

### Почему это ОДНА атомарная операция, а не серия мелких фиксов

Пока хотя бы один шаблон использует старый inline-синтаксис, `'unsafe-eval'`
убирать нельзя — иначе Alpine падает молча на этом шаблоне (Expression
Error в консоль, сама вёрстка рендерится, но весь интерактив — дропдауны,
мобильное меню, тема, cookie-баннер и т.д. — отваливается). Это ровно та
поломка, что уже случалась в этой сессии при первом включении CSP.
Значит: переписать ВСЕ шаблоны → проверить живьём КАЖДЫЙ интерактивный
элемент → и только потом одним коммитом убрать `'unsafe-eval'`.

### Что нужно сделать при старте

1. Найти все шаблоны с `x-data=`/`x-show=`/`x-on:`/`@click=` и т.п.
   (`grep -rl 'x-data=\|@click=\|x-show=' templates/`).
2. Для каждого уникального компонента вынести логику в
   `Alpine.data('componentName', () => ({...}))` в отдельном JS-файле
   (например `static/js/alpine-components.js`), заменить `x-data="{...}"`
   на `x-data="componentName"` в шаблонах.
3. Подключить `@alpinejs/csp` вместо обычного `alpinejs` в base.html/
   base_auth.html (CDN-тег меняется, версии/SRI пересчитать заново).
4. Пройтись живьём по каждой странице с интерактивом (тема, дропдауны,
   мобильное меню, cookie-баннер, live-пульс на матче, вайзард оценки) —
   до и после снятия `'unsafe-eval'`.
5. Только когда ВСЁ проверено — убрать `'unsafe-eval'` из
   `ContentSecurityPolicyMiddleware.POLICY` и задокументировать.

### Оценка объёма

Большая — затрагивает, по грубой прикидке, большинство шаблонов проекта
(любой с интерактивным UI). Не делать наспех / не в конце лимита.

## [ОТЛОЖЕНО] Прогнозы на матчи в стиле Sofascore

Зафиксировано: 2026-08-17, по запросу пользователя.
Статус: ждёт команды на старт. НЕ начинать самостоятельно.

### Суть

Добавить в DOPX полноценную систему прогнозов на матчи — ориентир по UX и
набору фич: **sofascore.com**. Не копировать вслепую, но при проектировании
каждого под-пункта опираться на то, как это реализовано там, и стремиться к
такому же уровню полировки.

### Известный на момент фиксации объём (уточнять при старте — sofascore
мог измениться, нужно будет заново пройтись по их UI перед реализацией)

1. **Интерфейс прогнозов**
   - UI для дачи прогноза на исход/счёт матча (как у sofascore — выбор
     исхода/точного счёта, отображение % проголосовавших по каждому
     варианту после того как сам проголосовал).
   - Отображение своих прошлых прогнозов и их точности.

2. **Push-уведомления на подписанные команды**
   - Использовать существующую инфраструктуру Web Push (см. `analytics`/
     PWA-фичи, `static/js/push.js` — уже есть база от П.5c из прошлой сессии).
   - Триггер: матч команды, на которую пользователь подписан (follow-граф,
     см. П.5b), скоро начинается — прислать пуш с призывом дать прогноз.
   - Нужно продумать тайминг (за сколько до матча слать) и анти-спам
     (не долбить, если пользователь уже прогнозировал).

3. **Автоматическое закрытие приёма прогнозов**
   - Как у sofascore: приём прогнозов прекращается в момент начала матча
     (или чуть раньше — уточнить их точный тайминг при реализации).
   - Скорее всего через celery beat периодическую задачу или сигнал на
     смену статуса матча (уже есть `ParserSyncRun`/`update_match_statuses`
     из прошлой сессии — можно перевесить логику закрытия туда же).

4. **Достижения под прогнозы**
   - Отдельная ветка бейджей (см. существующий каталог достижений,
     `users` app) — серии точных прогнозов, прогнозы на дерби и т.д.
     Дизайн конкретных бейджей — при реализации.

5. **Уведомления**
