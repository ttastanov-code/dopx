## [РЕШЕНО 2026-08-21] Битый текст тултипов ("Дербии002Дэксперт" вместо "Дерби-эксперт")

Баг-репорт пользователя: подсказка над иконкой бейджа показывала кривый
текст вместо "Дерби-эксперт". Причина — регресс из этой же сессии, побочный
эффект Alpine CSP-миграции (см. раздел выше): текст шёл через `escapejs()`
ПРЯМО в строковый литерал внутри `x-data="tooltipTrigger('...')"`.
`escapejs()` экранирует дефис как `-` — валидный JS, но CSP-евалуатор
`@alpinejs/csp` разбирает выражение `x-data` сам (это НЕ полноценный JS
eval) и не раскрывает `\uXXXX`-эскейпы внутри строковых литералов
аргументов — символы утекали в текст как есть.

Затронуто 4 места (везде тот же антипаттерн: динамический текст аргументом
в `x-data="компонент('...')"`), не только тултипы:

1. `tooltipTrigger` (`core/templatetags/tooltip_tags.py`,
   `templates/components/_tooltip_icon.html`) — сам баг-репорт.
2. `matchContextForm` (`templates/evaluations/context.html`) — **более
   серьёзный скрытый баг**: `supported_team` это UUID команды, UUID
   ВСЕГДА содержит дефисы → подсветка выбранной команды на шаге 1 вайзарда
   оценки могла молча не срабатывать (`supportedTeam === '{{ team.id }}'`
   сравнивал испорченное значение с чистым).
3. `contactForm` (`templates/core/contacts.html`) — email с дефисом ловил
   бы ту же порчу.
4. `pushSettings` (`templates/users/notification_settings.html`) — csrf-токен
   на практике не содержит спецсимволов (алфавит без дефисов), баг не
   проявлялся, но тот же хрупкий паттерн — исправлено для единообразия.
   Попутно исправлен независимый HTML-баг в этом же месте — незакрытый
   `<div x-data="pushSettings(...)"` (пропущенная `>`).

**Фикс:** все 4 места переведены с аргумента функции в `x-data(...)` на
обычные HTML `data-*`-атрибуты, читаемые в `init()` компонента через
`this.$el.dataset` — экранирование обычным HTML-escape() на сервере,
никакого JS-парсинга строкового литерала вообще не участвует. Это и есть
корректный паттерн передачи серверных данных в `@alpinejs/csp`-компонент;
взят за образец для всех будущих компонентов с динамическими данными.

**Не проверено живьём** (нет браузера в песочнице разработки) — только
синтаксис. Стоит открыть `/profile/` и глянуть тултип бейджа, плюс шаг 1
вайзарда оценки (подсветка выбранной команды) после деплоя.

## [РЕШЕНО 2026-08-21] Окно прогнозов: нижняя граница (было — без ограничения)

Баг-репорт пользователя: можно было проголосовать за исход матча хоть за
год вперёд — `Match.is_prediction_open()` проверял только `status ==
'scheduled' and now < start_time`, без нижней границы вообще.

**Сделано:** `Match.PREDICTION_WINDOW_DAYS = 5` (matches/models.py) —
окно прогноза открывается только за 5 дней до `start_time`, закрывается
по-прежнему стартовым свистком. `Match.prediction_opens_at()` — момент
открытия. `Match.prediction_window_not_yet_open()` — отдельный флаг для
виджета (третье состояние, кроме "открыто"/"закрыто после старта"):
`templates/predictions/_prediction_widget.html` теперь показывает "Прогнозы
откроются {{ дата }}" вместо пустого/задизейбленного вида без объяснения.
`predictions/services.py::submit_prediction` изменений не потребовал —
уже делегировал проверку в `is_prediction_open()`.

`PREDICTION_WINDOW_DAYS` — константа в коде (не settings.py), по аналогии
с уже существующими хардкоженными `timedelta(hours=48)` для
`voting_open_until` по всему проекту — так проще, отдельная задача
вынести такие константы в settings, если понадобится крутить их без
деплоя, не стоит прямо сейчас.

## [РЕШЕНО 2026-08-21] KFF публикует перенос раньше, чем меняет status/date в API

Зафиксировано: 2026-08-21, живой пример — матч Окжетпес–Кызылжар (KFF
external_id=1066). Изначальная гипотеза ("KFF ещё не обновил structured
status/date, только текстовый баннер") была ПРОВЕРЕНА и ОПРОВЕРГНУТА:
пользователь достал сырой JSON через `/staff/dashboard/parser/` (эндпоинт
"Детали матча") — `"status": "postponed"` и `"tour": 23` там присутствовали
корректно. Сигнал от KFF надёжен, проблема была на нашей стороне.

Найдено и исправлено ДВА независимых бага:

1. **`import_match_core` (`parsers/kff/importers.py`) не проверял
   `Match.manual_override` вообще** — только `update_match_statuses`
   (`parsers/tasks.py`) это делал. Полный синк сезона идёт через
   `import_match_core`, поэтому ручная пометка "перенесён вручную" переживала
   один цикл `update_match_statuses`, но откатывалась обратно на "scheduled"
   при следующем `sync_kff_premier_league`. Исправлено: `import_match_core`
   теперь тоже проверяет `manual_override` и, если он выставлен, не трогает
   `status`/`start_time`/`end_time`/`voting_open_until` пришедшего матча.
2. **Стейл-процесс Celery worker/beat** — код был исправлен и мигрирован, но
   уже запущенные `celery worker`/`celery beat` продолжали работать со
   старым кодом в памяти (Python-процессы не hot-reload'ятся на изменение
   файлов). Симптом "код поправил, migrate прогнал, а поведение всё равно
   старое" — решается ТОЛЬКО перезапуском обоих процессов. Зафиксировано как
   общий урок ниже, в разделе "Операционные напоминания".

Также добавлено поле `Match.tour` (`matches/migrations/0005_match_tour.py`)
— номер тура из KFF (`game_data.get("tour")`), устойчивый ориентир при
переносах (в отличие от `start_time`, номер тура не меняется вместе с
датой). Отображается в `_match_card.html`/`_match_header.html`, есть фильтр
по туру на `/matches/`. Плюс `Match.manual_override`
(`matches/migrations/0004_match_manual_override.py`) с двумя admin-action'ами
в `MatchAdmin`: "Пометить перенесённым вручную" / "Снять ручную пометку".
Плюс фикс отдельного бага в `MatchListView.get_queryset()` —
`status='postponed'`/`'cancelled'` раньше проваливались в необработанный
`else`-случай (показывали ВСЕ матчи вместо отфильтрованных).

## Мультисезонность/мультилиговость: баг главной таблицы + формат "кубок" + фильтрация списков по сезону

Зафиксировано: 2026-08-17, дополнено 2026-08-18. Находки 1 и 3 (включая
структурный слой историзации — только для игроков) выполнены 2026-08-21 по
явной команде пользователя. Находка 2 (формат "кубок") остаётся ОТЛОЖЕНА —
реальные данные Кубка Казахстана пока не планируется грузить в БД, это
risk-awareness запись, а не задача в работу.

### Находка 1 — [РЕШЕНО 2026-08-21] баг (сработал бы, как только появится 2-я активная лига)

Было: `core/views.py::standings_preview` брал `Season.objects.filter(is_active=True).first()`
БЕЗ фильтра по лиге — с одной активной лигой работало случайно правильно,
но как только у второй лиги появился бы свой активный сезон, какая таблица
попадёт на главную решала бы сортировка `Season.Meta.ordering = ['-year']`,
а не осмысленный выбор.

Сделано: добавлен `League.is_primary` (BooleanField с тем же
singleton-паттерном в `save()`, что и `Season.is_active`) — миграция
`leagues/migrations/0002_league_is_primary.py` (AddField + data-миграция,
автоматически помечает главной лигу текущего активного сезона, если он
есть, иначе первую лигу по алфавиту). Добавлен `Season.get_primary_active()`
(seasons/models.py) — единая точка правды "какой сезон сейчас показываем по
умолчанию" (активный сезон главной лиги, с fallback на старое поведение,
если `is_primary` ещё не проставлен). `standings_preview` и все списки из
находки 3 используют именно его.

### Находка 2 — архитектурный пробел: нет понятия "формат соревнования"

Ни `League`, ни `Match` не знают о существовании кубкового (на выбывание)
формата — только круговая таблица. Если завести Кубок Казахстана как
обычную `League` с активным сезоном, движок молча посчитает и покажет
бессмысленную W-D-L/очки таблицу (aggregates/tasks.py::recalculate_season_standings
жёстко предполагает круговой турнир). Нужно перед загрузкой реальных
данных кубка:
1. Поле формата на `League` (`format`: `league`/`cup` или `is_cup`
   BooleanField).
2. Поле раунда/стадии на `Match` (`round`/`stage`: групповой этап, 1/8,
   1/4, 1/2, финал, + возможно `leg` для двух матчей туда-обратно).
3. `standings_preview`/`recalculate_season_standings` должны пропускать
   лиги с `format='cup'` — им нужен отдельный виджет (сетка плей-офф), не
   таблица. Отдельная фронтенд-задача, не переиспользует текущий UI
   таблицы.

Не блокирует ничего прямо сейчас — просто предупреждение "не заводите
Кубок как обычную лигу в проде, пока это не сделано".

### Находка 3 — [РЕШЕНО 2026-08-21, быстрый слой] списки teams/players/coaches не фильтровались по сезону

Зафиксировано: 2026-08-18, по вопросу пользователя "что будет на этих
страницах, когда начнётся следующий сезон КПЛ". Проверено (на момент
обнаружения):

- `Season.save()` устроена правильно — при сохранении сезона с
  `is_active=True` все остальные сезоны ЭТОЙ лиги автоматически гасятся,
  так что "текущий сезон лиги" всегда однозначен.
- `TeamSeason` корректно пишется при каждом импорте матча — связь
  команда↔сезон в БД есть, ей просто никто не пользуется на списках.
- Но `TeamListView`/`PlayerListView`/`CoachListView`/`RefereeListView`
  (teams/players/coaches/referees `views.py`) вообще не фильтруют по
  сезону/лиге — `Team.objects.all()` и т.д. показывают ВСЁ, что когда-либо
  импортировано, одним списком навсегда.
- `is_active` у Player/Coach/Referee нигде программно не гасится (только
  выставляется в True при создании/реактивации) — сейчас декоративное
  поле, не сигнал "участвует в текущем сезоне".
- `Player.team`/`Coach.team` — одиночный FK "текущая команда", а не
  история по сезонам. При трансфере/смене сезона старая привязка просто
  перезатирается; carrier-история сохраняется только на уровне состава
  конкретного матча (`MatchLineupPlayer`), нигде не показывается как
  "карьера".

Итог: когда сезон закончится и начнётся следующий, вылетевшие команды и
ушедшие игроки/тренеры НЕ пропадут (это ожидаемо и не должно быть
починено удалением), но и никак не отделятся от текущего состава —
будут висеть в тех же общих списках навсегда вперемешку с актуальными.

**Сделано (быстрый слой, 2026-08-21):**

`TeamListView`/`PlayerListView`/`CoachListView` (teams/players/coaches
`views.py`) теперь по умолчанию фильтруют по `Season.get_primary_active()`
через `TeamSeason` (для players/coaches — по текущей команде игрока/тренера,
`team__teamseason__season=...`, а не по факту участия в конкретных матчах
сезона — проще и достаточно для цели "не мешать актуальный состав с
историческим"). Добавлен переключатель `?season=all` (компонент
`templates/components/_season_scope_toggle.html`, тег `query_transform` в
`core/templatetags/querystring_extras.py` сохраняет остальные GET-параметры
при переключении/пагинации). `RefereeListView` НЕ сезонится — явное решение
пользователя (судьи не привязаны к команде, список остаётся глобальным).

**Сделано (структурный слой — только для игроков, 2026-08-21):**

Полноценная историзация через новую модель (`PlayerSeason`/`CoachSeason` по
аналогии с `TeamSeason`) НЕ потребовалась — команда-по-сезонам для игрока
восстанавливается прямым запросом к уже существующему `MatchLineupPlayer`
(каждая запись состава жёстко привязана к факту участия в конкретном матче
конкретного сезона через `lineup.team`/`lineup.match.season`, задним числом
не переписывается — в отличие от `Player.team`, который хранит только
ТЕКУЩУЮ команду). `PlayerDetailView.get_context_data` (players/views.py)
группирует записи по (сезон, команда) в Python — если игрок менял клуб в
разгар сезона, получает две отдельные строки за один год, это корректное
отображение, не баг. Голы на отрезок сезон+команда — через `MatchEvent`,
дополнительным запросом по id матчей отрезка. Блок "По сезонам" —
`templates/players/detail.html`, между "Историей выступлений" и "Лучшими
матчами".

Для тренеров та же историзация СТРУКТУРНО НЕВОЗМОЖНА (см. находку 4 ниже):
KFF не хранит историю назначений тренеров вообще, ни в одном матче, ни в
каком-либо виде источника — заполнить `CoachSeason`/аналогичный запрос было
бы физически нечем. Осознанно не делается, не техдолг.

### Находка 4 — [РЕШЕНО 2026-08-18] статистика тренера не разделялась по "при каком тренере сыгран матч"

Зафиксировано: 2026-08-18, по живому примеру пользователя: тренер Самат
Смаков пришёл в «Атырау» и провёл как тренер 2 матча, но на сайте у него
показано 21 (= почти весь сезон клуба).

Гипотеза о собственном баге (нестрогий guard в `import_coaches`,
позволявший `sync_recent_matches` переписывать `home_coach`/`away_coach`
задним числом при каждом периодическом ресинке) НЕ подтвердилась как
основная причина. Проверка через `resync_finished_match_coaches --team
Атырау --dry-run` (реальные запросы к KFF `/lineup` по каждому
завершённому матчу) показала: 0 изменений из 21 матча — то есть KFF
СЕГОДНЯ отдаёт текущего тренера даже для матчей трёхмесячной давности.
Пользователь подтвердил вручную на сайте kff.kz: при смене тренера клуба
KFF просто отвязывает старого и привязывает нового — история назначений
не хранится вообще, ни в конкретном матче, ни где-либо ещё в их системе.
Итог: это ограничение источника данных, а не решаемый баг импорта —
"кто вёл конкретный исторический матч" физически не восстановить.

**Что сделано вместо починки данных (раз данных для починки не существует):**

1. `parsers/kff/importers.py::import_coaches` — guard всё равно оставлен
   (не даёт `home_coach`/`away_coach` меняться у уже `finished` матча):
   не чинит историю, но хотя бы не даёт ей "плыть" туда-сюда при каждом
   ресинке одного и того же (заведомо неточного) значения.
2. `coaches/views.py`/`templates/coaches/list.html`/`detail.html` —
   счётчик "Матчей" убран целиком (был системно недостоверен), заменён на
   "Оценок" (`evaluations_count`/`total_evaluations` через
   `CoachEvaluation` — эта привязка НЕ страдает той же проблемой: болельщик
   оценивает конкретного тренера вскоре после матча, эта запись не
   переписывается задним числом при смене тренерского штаба).
3. Блок "Последние матчи" на странице тренера переименован в "Форма
   команды" — те же данные (последние матчи текущего клуба тренера), но
   честно подписаны как командные, с явным пояснением под заголовком, а
   не выданы за персональную статистику тренера.
4. `resync_finished_match_coaches` (core/management/commands/) оставлена
   в проекте — рабочий инструмент диагностики на будущее (например, если
   KFF когда-нибудь начнёт отдавать историю, или для разовой проверки
   конкретной команды/тренера).

**Не проверено и не тронуто:** аналогичный риск для `Player.team`
(`parsers/kff/importers.py::get_or_create_player` тоже перезаписывает
команду при каждом импорте состава) — НО фактическая статистика "матчей"
игрока считается через `MatchLineupPlayer` (реальное историческое участие
в конкретном составе конкретного матча), а не через текущий `Player.team`
— в отличие от тренеров, эта привязка иммутабельна и не подвержена той

<details>
<summary>Исходный план (для истории)</summary>

Сейчас `dopx/middleware.py::ContentSecurityPolicyMiddleware` держит
`'unsafe-eval'` и `'unsafe-inline'` в `script-src`, потому что Alpine.js по
всем шаблонам используется в inline-форме (`x-data="{...}"`,
`x-show="..."`, `@click="..."` прямо в HTML-атрибутах) — Alpine компилирует
эти выражения через `new AsyncFunction(...)`, что CSP трактует как eval.

Цель: перейти на `@alpinejs/csp` — сборку Alpine, которая ЗАПРЕЩАЕТ inline
x-data-выражения и требует регистрировать компоненты через `Alpine.data(...)`
в обычном JS-файле. После этого `'unsafe-eval'` можно убрать из CSP
полностью.

1. Найти все шаблоны с `x-data=`/`x-show=`/`x-on:`/`@click=` и т.п.
2. Для каждого уникального компонента вынести логику в
   `Alpine.data('componentName', () => ({...}))` в отдельном JS-файле,
   заменить `x-data="{...}"` на `x-data="componentName"` в шаблонах.
3. Подключить `@alpinejs/csp` вместо обычного `alpinejs`.
4. Пройтись живьём по каждой странице с интерактивом — до и после снятия
   `'unsafe-eval'`.
5. Убрать `'unsafe-eval'` из `ContentSecurityPolicyMiddleware.POLICY`.

</details>

## [РЕШЕНО 2026-08-21] Петли удержания (retention loops) — 4 штуки

По явной команде пользователя ("нужна регулярная причина вернуться")
реализованы все 4 выбранные петли, поверх уже существующей инфраструктуры
`notifications` app (явный `notification_type`, дайджест-режим,
fan-out-рассылки пачками).

1. **Дедлайны голосования/оценки** → **[ПЕРЕОСМЫСЛЕНО 2026-08-21] приглашение
   к прогнозу в стиле Sofascore.** Оценки (evaluations) уже имели
   `notify_voting_closing_soon` (`notifications/tasks.py`) — не трогали.
   `notify_prediction_closing_soon` (за час до `Match.start_time`, только
   тем, кто ещё не поставил прогноз на этот матч, `crontab(minute='*/30')`)
   изначально был чисто urgency-напоминанием ("закрывается — успейте"), по
   явному запросу пользователя переписан на приглашающий тон ("команда А
   играет с командой Б — как думаете, кто победит?", по мотивам того, как
   это делает Sofascore) и расширен с email-only на три канала сразу: email
   (переписанный `templates/emails/prediction_closing.html`) + push
   (`notifications.services.send_push_to_user`, best-effort, тот же паттерн,
   что `notify_followers_match_activity`) + in-app `Notification`
   (`notification_type='prediction_closing'`, раньше не создавался вообще).
   Дедуп сознательно не добавлен — в узком часовом окне повторное
   приглашение при следующем тике `crontab` это ОК, ближе к
   Sofascore-паттерну, чем риск не достучаться из-за пропущенного тика.
2. **Персональная недельная сводка.** Новая задача `send_weekly_summary`
   (понедельник 10:00) — на каждого опт-инувшего пользователя: сколько
   оценок/прогнозов за 7 дней, точность прогнозов (только по решённым
   исходам), общий "матч недели" по `aggregates.MatchAggregate.avg_entertainment`.

   сводка сама по себе уже дайджест, оборачивать её ещё раз бессмысленно).
3. **«Ваш прогноз vs сообщество».** Новая задача `notify_prediction_results`

   lookback 6 часов) — персонализированное письмо+in-app уведомление

   распределились голоса сообщества (`predictions.services.prediction_counts`).
   Дедупликация — по отсутствию `Notification(notification_type=
   'prediction_result', related_match=match, user=user)` для пары.
4. **Серии и шер-карточки.** `User.prediction_streak`/`last_prediction_date`

   существовавшего `evaluation_streak` для оценок, считается по

   шлёт письмо/дайджест. Share-карточка — `core/services/share_cards.py::
   build_streak_share_card` (тот же Pillow-рендер+кэш-по-хэшу паттерн, что
   у карточки матча), `/share/streak/<username>/<evaluation|prediction>/card.png`

### Как тестировать retention loops без реальных матчей

Зафиксировано 2026-08-21: у KPL нет матчей ближайшие 2 недели, но
проверить виджет прогнозов и все уведомления нужно уже сейчас. Два новых
инструмента для этого:

1. **`python manage.py simulate_match_timing`** (новое,
   `core/management/commands/simulate_match_timing.py`) — без аргументов
   выводит список последних матчей и их id; с id — двигает УЖЕ существующий
   в БД матч (любого статуса) по времени/статусу/счёту и ставит
   `manual_override=True`, чтобы автосинк KFF не перезаписал подделку на
   следующем цикле. Не создаёт синтетические матчи с нуля — переиспользует
   реальные team/league/season FK, это безопаснее для допущений
   аггрегатов/парсера. `--release` возвращает матч под автосинк обратно.
   Примеры — в докстринге самой команды.
2. **Ручной запуск задач через `/staff/dashboard/parser/`** — раньше
   (задача #93) инструмент "Ручной запуск celery-задач" умел запускать
   ТОЛЬКО задачи из `parsers.tasks` (маршрутизация модуля была захардкожена
   в `dashboard/parser_tools.py::trigger_task()`). Расширено: добавлены
   кнопки `notify_prediction_closing_soon`/`notify_prediction_results`/
   `send_weekly_summary` (из `notifications.tasks`), маршрутизация модуля
   теперь по имени задачи (`_TASK_MODULES` в том же файле).

Типовой сценарий: `simulate_match_timing <id> --status scheduled
--start-in-minutes 50` (матч через 50 минут — открывает окно прогноза И
часовое окно приглашения) → зайти на `/matches/<id>/`, поставить прогноз →
нажать кнопку `notify_prediction_closing_soon` в `/staff/dashboard/parser/`
→ проверить письмо/push/колокольчик уведомлений. Затем `simulate_match_timing
<id> --status finished --home-score 2 --away-score 1` → кнопка
`notify_prediction_results` → проверить письмо "прогноз vs результат".
`send_weekly_summary` не требует симуляции времени матча — считает по
`created_at`/`completed_at` за последние 7 дней, сегодняшняя тестовая
активность уже попадёт в неё.

## [БУДУЩЕЕ, считаю обязательным] Технический долг, накопленный за эту сессию

Список моих собственных наблюдений (не запрошено пользователем явно, но
считаю важным зафиксировать, пока не забылось) — приоритет обозначен, но
ничего не начинать без команды:

1. **[Высокий приоритет] Убрать `'unsafe-inline'` из CSP** — последний
   оставшийся небезопасный флаг в `ContentSecurityPolicyMiddleware.POLICY`
   (`'unsafe-eval'` уже убран). Требует nonce/hash-рефакторинга КАЖДОГО
   инлайнового `<script>` и `style="..."` по всем шаблонам — по объёму
   сопоставимо с только что завершённым Alpine-рефакторингом, возможно
   больше (инлайновых `style=` в проекте заметно больше, чем было
   `x-data=`). Отдельный продуктовый цикл, не однодневная задача.
2. **[Средний] `parsers/kff/referee_scraper.py` — удалить файл.** Функция
   `scrape_referees` подтверждена мёртвым кодом (не импортируется нигде),
   переписана с хардненингом как временная мера, потому что `rm` не
   работает через файловые инструменты этой среды на примонтированной
   папке — нужно, чтобы пользователь удалил файл вручную на своей машине.
3. **[Средний] Прямой доступ к Gunicorn должен быть закрыт файрволом.**
   `core/utils.py::get_client_ip()` теперь корректно доверяет цепочке
   `X-Forwarded-For` через `TRUSTED_PROXY_COUNT`, но это НЕ замена сетевой
   защиты — если Gunicorn слушает публичный интерфейс напрямую (в обход
   nginx), у атакующего в заголовке будет ровно один поддельный элемент,
   который и окажется "на доверенной позиции". Это инфраструктурный шаг
   вне моих возможностей (security group/firewall на сервере).
4. **[Средний] Реальные шрифты Inter для Pillow-рендера share-карточек.**
   `core/services/share_cards.py` сейчас рисует текст Liberation Sans
   (метрически близкий к Arial, не Inter) — из-за отсутствия сетевого
   доступа для скачивания `.ttf` в этой сессии. Если/когда в репозиторий
   попадут `static/fonts/Inter-Bold.ttf`/`Inter-Regular.ttf` — поменять
   две строки в `_font()`, остальной код уже не завязан на конкретный файл.
5. **[Низкий] Точность прогнозов как метрика доверия.** Сейчас
   `trust_score`/`xp_multiplier()` считаются только по оценкам
   (evaluations). Осмысленный источник, но с появлением прогнозов
   (объективно проверяемый исход, в отличие от субъективных оценок)
   стоило бы подумать, влияет ли точность прогнозов на `trust_score` —
   не делал этого сейчас: это меняет уже работающую формулу доверия,
   продуктовое решение не мне принимать в одиночку.
6. **Локальная сверка миграций.** Все миграции в проекте написаны вручную
   (нет `manage.py makemigrations` в песочнице разработки) — рекомендую
   периодически (не только после этой сессии) прогонять
   `python manage.py makemigrations --check --dry-run` локально, чтобы
   ловить рассинхрон между моделями и файлами миграций раньше, чем он
   проявится как реальная ошибка на проде.
