## [ОТЛОЖЕНО] Alpine.js → CSP-safe сборка (@alpinejs/csp)

Зафиксировано: 2026-08-17. Отложено из-за недельного лимита (94% использовано
на момент решения) — риск не успеть атомарно завершить рефакторинг и оставить
CSP в переходном ломающемся состоянии. Начать в след. сессии со свежим лимитом.

### Суть

Сейчас `dopx/middleware.py::ContentSecurityPolicyMiddleware` держит
`'unsafe-eval'` и `'unsafe-inline'` в `script-src`, потому что Alpine.js по
всем шаблонам используется в inline-форме (`x-data="{...}"`,
`x-show="..."`, `@click="..."` прямо в HTML-атрибутах) — Alpine компилирует
эти выражения через `new AsyncFunction(...)`, что CSP трактует как eval.

Цель: перейти на `@alpinejs/csp` — сборку Alpine, которая ЗАПРЕЩАЕТ inline
x-data-выражения и требует регистрировать компоненты через `Alpine.data(...)`
в обычном JS-файле. После этого `'unsafe-eval'` (и в идеале `'unsafe-inline'`
для script-src, через nonce/hash) можно убрать из CSP полностью.

### Почему это ОДНА атомарная операция, а не серия мелких фиксов

Пока хотя бы один шаблон использует старый inline-синтаксис, `'unsafe-eval'`
убирать нельзя — иначе Alpine падает молча на этом шаблоне (Expression
Error в консоль, сама вёрстка рендерится, но весь интерактив — дропдауны,
мобильное меню, тема, cookie-баннер и т.д. — отваливается). Это ровно та
поломка, что уже случалась в этой сессии при первом включении CSP.
Значит: переписать ВСЕ шаблоны → проверить живьём КАЖДЫЙ интерактивный
элемент → и только потом одним коммитом убрать `'unsafe-eval'`.

### Что нужно сделать при старте

1. Найти все шаблоны с `x-data=`/`x-show=`/`x-on:`/`@click=` и т.п.
   (`grep -rl 'x-data=\|@click=\|x-show=' templates/`).
2. Для каждого уникального компонента вынести логику в
   `Alpine.data('componentName', () => ({...}))` в отдельном JS-файле
   (например `static/js/alpine-components.js`), заменить `x-data="{...}"`
   на `x-data="componentName"` в шаблонах.
3. Подключить `@alpinejs/csp` вместо обычного `alpinejs` в base.html/
   base_auth.html (CDN-тег меняется, версии/SRI пересчитать заново).
4. Пройтись живьём по каждой странице с интерактивом (тема, дропдауны,
   мобильное меню, cookie-баннер, live-пульс на матче, вайзард оценки) —
   до и после снятия `'unsafe-eval'`.
5. Только когда ВСЁ проверено — убрать `'unsafe-eval'` из
   `ContentSecurityPolicyMiddleware.POLICY` и задокументировать.

### Оценка объёма

Большая — затрагивает, по грубой прикидке, большинство шаблонов проекта
(любой с интерактивным UI). Не делать наспех / не в конце лимита.

## [ОТЛОЖЕНО] Прогнозы на матчи в стиле Sofascore

Зафиксировано: 2026-08-17, по запросу пользователя.
Статус: ждёт команды на старт. НЕ начинать самостоятельно.

### Суть

Добавить в DOPX полноценную систему прогнозов на матчи — ориентир по UX и
набору фич: **sofascore.com**. Не копировать вслепую, но при проектировании
каждого под-пункта опираться на то, как это реализовано там, и стремиться к
такому же уровню полировки.

### Известный на момент фиксации объём (уточнять при старте — sofascore
мог измениться, нужно будет заново пройтись по их UI перед реализацией)

1. **Интерфейс прогнозов**
   - UI для дачи прогноза на исход/счёт матча (как у sofascore — выбор
     исхода/точного счёта, отображение % проголосовавших по каждому
     варианту после того как сам проголосовал).
   - Отображение своих прошлых прогнозов и их точности.

2. **Push-уведомления на подписанные команды**
   - Использовать существующую инфраструктуру Web Push (см. `analytics`/
     PWA-фичи, `static/js/push.js` — уже есть база от П.5c из прошлой сессии).
   - Триггер: матч команды, на которую пользователь подписан (follow-граф,
     см. П.5b), скоро начинается — прислать пуш с призывом дать прогноз.
   - Нужно продумать тайминг (за сколько до матча слать) и анти-спам
     (не долбить, если пользователь уже прогнозировал).

3. **Автоматическое закрытие приёма прогнозов**
   - Как у sofascore: приём прогнозов прекращается в момент начала матча
     (или чуть раньше — уточнить их точный тайминг при реализации).
   - Скорее всего через celery beat периодическую задачу или сигнал на
     смену статуса матча (уже есть `ParserSyncRun`/`update_match_statuses`
     из прошлой сессии — можно перевесить логику закрытия туда же).

4. **Достижения под прогнозы**
   - Отдельная ветка бейджей (см. существующий каталог достижений,
     `users` app) — серии точных прогнозов, прогнозы на дерби и т.д.
     Дизайн конкретных бейджей — при реализации.

5. **Уведомления**
   - Расширить существующую систему notifications (см. `notifications` app,
     явный `notification_type` из прошлой сессии) под события прогнозов:
     результат прогноза известен, бейдж получен и т.д.

6. **Рейтинги/лидерборды прогнозистов**
   - Отдельный лидерборд по точности прогнозов, возможно с сегментацией
     (как есть сейчас для оценок — фильтры по городу/лиге).
   - "Может" в формулировке пользователя — уточнить приоритет при старте.

### Что нужно сделать ПЕРЕД началом реализации (не сейчас)

- Заново пройтись по sofascore.com (веб + при возможности мобильное
  приложение) прямо перед стартом — зафиксировать актуальный UX/тайминги,
  не полагаться на память об этом файле.
- Оценить объём как отдельный продуктовый цикл (архитектура моделей для
  прогнозов, миграции, celery-таски, шаблоны, push-инфраструктура) —
  это большая фича, не однодневный фикс.
