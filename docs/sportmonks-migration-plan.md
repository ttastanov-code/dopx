# План перехода DOPX с KFF на Sportmonks

Срок: 14 дней trial (до 2026-09-22). Сервер и Celery/Docker остановлены на время работ.

## 0. Принцип безопасности

Ничего не удаляем и не переключаем, пока новый путь не проверен. Весь код KFF (`parsers/kff/`) остаётся нетронутым и рабочим до самого cutover в фазе 6 — это гарантия отката, если что-то в Sportmonks-варианте пойдёт не так. Новый код живёт параллельно в `parsers/sportmonks/`, ничего не трогая в старом.

Ключевое архитектурное решение: **не переиспользуем поле `external_id`** (там уже лежат id из KFF JSON API на League/Season/Team/Player/Coach/Referee/Match/Stadium). Добавляем новое поле `sportmonks_id` (unique, nullable, indexed) на те же модели. Это чистая additive-миграция, ничего не ломает, историю не трогает.

## 1. Модели и миграции (фаза 1)

Добавить `sportmonks_id` на: `League`, `Season`, `Team`, `Player`, `Coach`, `Referee`, `Match`, `Stadium`. Плюс два новых необязательных поля под находки из API:

- `Match.referee_crew = JSONField(null=True, blank=True)` — ассистенты и четвёртый судья (главный судья остаётся в существующем FK `referee`, туда пишем `type_id=6`).
- Новая модель `PlayerSidelined` (player FK, category, start_date, end_date) — под бейдж "недоступен" на карточке игрока.

Ничего из существующих полей не удаляем на этом шаге (`kff_website_id`, `roster_absence_streak`, `ParserSyncRun`, `ParserDiscrepancy` остаются как есть до фазы 6).

## 2. settings.py

```python
SPORTMONKS_API_TOKEN = os.getenv('SPORTMONKS_API_TOKEN')
SPORTMONKS_LEAGUE_ID = 393          # Kazakhstan Premier League
SPORTMONKS_BASE_URL = 'https://api.sportmonks.com/v3/football'
SPORTMONKS_LOCALE = 'ru'
```

Токен только через env, никогда в коде/репозитории.

## 3. Клиент (`parsers/sportmonks/client.py`)

Сильно проще KFF-клиента: платный API, блокировок по TLS-фингерпринту нет, значит не нужны ни `curl_cffi`, ни circuit breaker, ни proxy rotation, ни cookie jar, ни global pace gate. Нужно только:

- Обычный `requests.Session` с `api_token` и `locale=ru` в параметрах по умолчанию.
- Ретрай с backoff (2-3 попытки) только на `429`/`5xx`/сетевые ошибки, не на `403/404` (это осмысленные ответы API, не блокировка).
- Чтение `x-ratelimit-remaining` из ответа и warning в лог, если остаток по какой-то entity падает ниже 10%, чтобы заранее видеть аномальный расход, а не только по факту 429.
- Явное разделение "лёгких" вызовов (bulk livescores, только состояние и счёт) и "тяжёлых" (include=lineups;events;statistics;referees;coaches) — это основа для экономии лимита в фазе 4.

понадобится сверка с уже накопленными данными — просто сейчас применять

## 4a. Реконсиляция существующих записей (архив, не выполняется)

Это единственный по-настоящему рискованный для истории шаг, поэтому выносим отдельно и делаем строго до того, как импортёр начнёт что-либо писать в проде.

- **Команды (16 штук)**: вручную построить статическую таблицу `{team_name -> sportmonks_team_id}`, свериться глазами. Маленький и стабильный список, авто-фаззи тут не нужен, риск ошибки от автоматики выше, чем от ручной сверки 16 строк.
- **Тренеры и судьи**: в Sportmonks они с самого начала стабильные сущности, но в базе DOPX уже есть исторические Referee/Coach, заведённые через `get_or_create_referee_by_name` из свободного текста KFF. Нужен скрипт, который для каждого нового sportmonks-referee/coach ищет совпадение среди существующих записей через уже готовый `normalize_kz` + `difflib` (тот же принцип, что в `dedupe_referees_coaches.py`), с порогом на авто-совпадение и списком на ручной review для пограничных случаев.
- **Игроки**: то же самое, сопоставление по (команда + нормализованное имя). Автоматически мэтчим уверенные совпадения, спорные — в отчёт на ручную проверку, ничего не мержим втихую.

Результат фазы 2 — csv/json с финальным маппингом, по которому `sportmonks_id` проставляется на существующие строки одной командой, без создания дублей.

## 5. Импортёры (`parsers/sportmonks/importers.py`, фаза 3) — ГОТОВО, ждёт живого прогона

Пользователь подтвердил: раз база пустая (flush), бэкафилл делаем сразу по всем 3 доступным без доп. оплаты сезонам — 2024, 2025, 2026. Написан `parsers/management/commands/sync_sportmonks_season.py` (`--year`, `--limit`).

Все маппинги ниже проверены ЖИВЫМ запросом 2026-09-08 к реальному сыгранному матчу КПЛ (fixture 19681993, Тобол vs Кайсар) через тестовый ключ триала — не придуманы:

- `state.developer_name` (СТАБИЛЬНАЯ строка, не числовой `state_id`) → `Match.status`, таблица `STATE_MAP` в importers.py. Подтверждено: `"FT"` → finished. Остальные значения — по документированной схеме Sportmonks, не встречены в тестовом матче, код не падает и не молчит на неизвестном значении (тот же паттерн, что `STATUS_MAP` у KFF).
- `referees[].type_id` 6/7/8/9 (developer_name REFEREE/REFEREE_TWO/REFEREE_THREE/REFEREE_FOUR) → главный судья в `Match.referee`, остальные три — в `Match.referee_crew` JSON. Подтверждено вживую с реальными именами.
- `lineups[].type_id` 11=LINEUP (старт), 12=BENCH (запас) — подтверждено вживую.
- `formation_field` ("row:col", напр. "3:5") → зона L/C/R/LC/RC — ЭВРИСТИКА (группировка игроков одной строки по количеству, см. `_compute_field_positions`), НЕ подтверждённая на разных формациях — обязательно сверить визуально на странице матча после первого прогона.
- Позиция игрока: `position_id` 24/25/26/27 → GK/D/M/F — подтверждено вживую (вратарь=24, защитник=25, нападающий=27), напрямую совместимо с существующей схемой `players/positions.py`.
- Статистика матча: **командная** — `fixture.statistics[].type.developer_name` (НЕ локализованное `type.name` — оно машинный перевод, ненадёжно для логики) → `MatchTeamStatistics`, таблица `TEAM_STAT_DEV_NAME_MAP`, 15 полей смэтчено из 34 реально пришедших типов, остальное — в `raw`. **Игровая** — обнаружено, что приходит НЕ отдельным `statistics`-массивом, а внутри `lineups[].details` (include `lineups.details.type`) → `MatchPlayerStatistics`, таблица `PLAYER_STAT_DEV_NAME_MAP`.
- События: `events[].type.developer_name` → `EVENT_DEV_NAME_MAP`. Подтверждено вживую: GOAL, PENALTY, SUBSTITUTION, YELLOWCARD (для замены `player_id`=вышел на поле, `related_player_id`=ушёл с поля — проверено на реальной замене). Own goal / красная / незабитый пенальти / VAR — не встретились в тестовом матче, замаплены по документации, не проверены живым примером.
- Тур/раунд: `round.name` — просто число строкой ("21"), подтверждено вживую. Никакого отдельного запроса `/rounds/{id}` не требуется.
- Формация (строка "4-4-2" для отображения) — отдельный include `formations`, подтверждено вживую, не нужно выводить из `formation_field`.
- Время начала матча (`starting_at`) — предположительно UTC (по документации Sportmonks), НЕ проверено на реальном совпадении с расписанием — свериться на первом же живом матче, см. `_parse_starting_at`.

Синтаксис проверен (`py_compile`), живой прогон через Django (`sync_sportmonks_season --year 2026 --limit 6`, затем сверка вручную на странице матча) — следующий шаг, делает пользователь локально.

## 6. Celery-таски и расписание, с учётом лимита (фаза 4)

Правило №1, уже проговорили: **никогда не дёргать матчи в цикле по одному** во время live-опроса. Всегда один bulk-вызов `livescores` на всю лигу.

Двухуровневая схема опроса:

1. **Лёгкий опрос** (раз в 1-2 минуты, как сейчас `scope='tight'`): один вызов bulk `livescores/inplay`, без тяжёлых include. Смотрим, у каких матчей поменялся счёт/`state_id` по сравнению с тем, что уже в базе.
2. **Тяжёлая догрузка** — только для матчей, где на шаге 1 обнаружено реальное изменение: отдельный вызов с `include=lineups;events;statistics;referees;coaches` именно по этому матчу, не по всем.

Даже в день с 5-6 переносами это на порядок дешевле лимита (мы это уже прикидывали: 240-720 запросов в час против лимита 2000 в час на entity, и это ещё без экономии на "дёргать только изменившееся").

Новые таски (`parsers/sportmonks/tasks.py`):

- `sportmonks_sync_season` — раз в сутки, полная синхронизация календаря сезона.
- `sportmonks_update_live` — раз в 1-2 минуты, двухуровневая схема выше.
- `sportmonks_update_upcoming` — раз в 30 минут, подтягивает составы для матчей в ближайшие 1-3 часа (составы у Sportmonks появляются за 10-15 минут до начала, это подтверждено менеджером).
- `sportmonks_health_check` — лёгкий пинг раз в несколько часов для дашборда, не критично как было с KFF, но полезно для видимости.
- `sportmonks_sync_sidelined` — раз в сутки, под новую фичу с бейджем "недоступен".

Всё, что сейчас тянет `sync_kff_player_meta`/`photo_scraper` (roster-absence эвристика, поиск фото на публичном сайте) — не переносим вообще, Sportmonks отдаёт актуальный состав напрямую через squads endpoint, эвристика больше не нужна.

## 7. Новые фичи из находок (фаза 5)

- Статистика матча рядом с "ДНК матча" — данные уже приходят через фазу 3, тут только фронтенд/шаблон.
- Форма команды (последние 5 W/D/L) — **не тянуть отдельным полем из API**, считать на лету из уже имеющихся в базе Match, это бесплатно и не тратит лимит вообще.
- `PlayerSidelined` → бейдж "недоступен" на карточке игрока.
- `Match.referee_crew` → показывать полную бригаду судей на странице матча, не только главного.
- Трофеи клуба — низкий приоритет, в бэклог, не блокирует переход.

## 8. Cutover и уборка (фаза 6, ближе к концу/после 14 дней)

1. Прогнать `sportmonks_sync_season` и `sportmonks_update_live` в дневном режиме несколько дней параллельно с уже работающим KFF-пайплайном (KFF продолжает писать как раньше, sportmonks-таски пока просто пишут в новые поля и логируют расхождения, ничего не переключено).
2. Сверить результат на живых матчах: счёт, события, составы, судьи — совпадает ли с тем, что уже даёт KFF.
3. Только после этого — переключить `CELERY_BEAT_SCHEDULE` на sportmonks-таски, KFF-таски закомментировать (не удалять) как аварийный откат.
4. Продержать так несколько дней в проде.
5. Финальная уборка, только когда всё стабильно:
   - удалить `parsers/kff/referee_scraper.py` (уже сейчас мёртвый код, можно убрать в любой момент, не дожидаясь остального);
   - удалить `curl_cffi` из requirements.txt и весь связанный с ним код (circuit breaker, cookie jar, pacing gate, proxy rotation в `client.py`/`photo_scraper.py`);
   - убрать `PARSER_SETTINGS['PROXY_POOL']` / `KFF_PROXY_POOL`;
   - убрать `sync_kff_player_meta` и связанные с roster-absence вещи, миграцией убрать `Player.roster_absence_streak`;
   - `kff_website_id` — не удалять миграцией, просто перестать заполнять (дешевле и безопаснее, чем деструктивная миграция ради поля, которое никому не мешает);
   - переименовать/обобщить `ParserSyncRun`/`ParserDiscrepancy` под универсальный источник (добавить поле `source`), обновить дашборд;
   - прогнать `dedupe_referees_coaches` последний раз, закрыть эпоху KFF-дублей.
