# Деплой DOPX: как всё устроено и что делать

Этот документ написан для человека, который не работал с Docker раньше.
Сначала — что это вообще такое и зачем, потом — пошаговая инструкция.

## Что такое Docker и зачем он тут

Сейчас проект запускается командой `python manage.py runserver` — это
режим для разработки, Django сам прямым текстом предупреждает, что его
нельзя использовать в бою: он однопоточный, не умеет нормально
переживать нагрузку и падение процесса.

Docker — это способ упаковать приложение вместе со ВСЕМ, что ему нужно
для работы (конкретная версия Python, все библиотеки, системные пакеты)
в один "контейнер" — изолированную коробку, которая одинаково запустится
что на твоём ноутбуке, что на любом сервере. Не нужно вручную ставить
Python нужной версии, PostgreSQL, Redis и 130 пакетов на сервере руками —
Docker сделает это по описанию, которое лежит в репозитории.

## Из чего состоит стек

Продакшн DOPX — это не один процесс, а пять контейнеров, которые вместе
образуют полноценный сайт:

**nginx** — единственная дверь снаружи. Принимает все запросы из
интернета, отдаёт статику и картинки напрямую (быстро), а всё остальное
передаёт дальше в Django. Также будет отвечать за HTTPS-сертификат.

**web** — сам Django-сайт, запущенный через gunicorn (прод-сервер
вместо `runserver`). Обрабатывает запросы, которые нельзя обслужить
статикой: показ страниц, вход, оценка матчей и т.д.

**celery_worker** — обработчик фоновых задач: синхронизация матчей с
сайта КФФ, пересчёт агрегатов и таблиц, рассылка email/push-уведомлений.
Всё, что не должно тормозить ответ пользователю, уходит сюда.

**celery_beat** — "будильник" для celery_worker: по расписанию (каждые
10 минут, раз в час, раз в сутки — см. `CELERY_BEAT_SCHEDULE` в
`dopx/settings.py`) ставит задачи в очередь. Должен быть только один
экземпляр — это не воркер, а планировщик.

**db** (PostgreSQL) и **redis** — база данных и Redis (он тут в трёх
ролях сразу: очередь задач для Celery, кэш Django, кэш агрегатов).

Все пять общаются друг с другом внутри отдельной docker-сети по именам
(`db`, `redis`, `web`...) — снаружи виден только nginx на портах 80/443.

## Файлы, которые появились в проекте

- `Dockerfile` — рецепт сборки образа (какой Python, какие системные
  пакеты, как копируется код).
- `docker-compose.yml` — описание всех пяти контейнеров и того, как они
  связаны (сети, тома для хранения данных, переменные окружения).
- `docker/entrypoint.sh` — скрипт, который выполняется при старте
  каждого контейнера: ждёт готовности базы, накатывает миграции, собирает
  статику (только в web-контейнере).
- `docker/nginx.conf` — настройки nginx.
- `.env.example` — шаблон переменных окружения (пароли, ключи, домен).
  Реальный `.env` в git не попадает.
- `.dockerignore` — что не должно попадать внутрь образа (дампы БД,
  чужие виртуальные окружения, секреты).

## Пошаговый запуск (первый раз, локально — проверить, что всё работает)

1. Установи Docker Desktop (Mac/Windows) или Docker Engine + Docker
   Compose plugin (Linux) — на официальном сайте docker.com, дальше
   везде просто `docker` и `docker compose` в терминале.

2. Скопируй шаблон переменных окружения и заполни его:
   ```
   cp .env.example .env
   ```
   Открой `.env` и заполни минимум: `SECRET_KEY` (сгенерировать можно
   командой ниже), `DB_PASSWORD` (придумай любой надёжный пароль — он
   же станет паролем от Postgres внутри контейнера), `ALLOWED_HOSTS` и
   `CSRF_TRUSTED_ORIGINS` (домен сайта, для локальной проверки можно
   `localhost` / `http://localhost`).
   ```
   docker run --rm python:3.12-slim python -c "import secrets; print(secrets.token_urlsafe(50))"
   ```

3. Собери образы и подними весь стек:
   ```
   docker compose up -d --build
   ```
   Первый раз это займёт несколько минут (скачивание базовых образов,
   установка ~130 Python-пакетов). После этого `entrypoint.sh` сам
   применит миграции и соберёт статику — ничего руками делать не нужно.

4. Проверь, что всё поднялось:
   ```
   docker compose ps
   ```
   Все сервисы должны быть в статусе `running` (для db/redis — ещё и
   `healthy`).

5. Открой в браузере `http://localhost` — должен показаться сайт.

6. Если нужен доступ в `/admin/`, а автосоздание суперпользователя через
   `.env` не настраивал — создай вручную:
   ```
   docker compose exec web python manage.py createsuperuser
   ```

## Полезные команды на каждый день

Посмотреть логи (например, если что-то не работает):
```
docker compose logs -f web
docker compose logs -f celery_worker
```

Зайти внутрь контейнера (например, чтобы руками выполнить management-команду):
```
docker compose exec web python manage.py <команда>
```

Перезапустить после изменения кода (Docker не подхватывает изменения
автоматически, в отличие от `runserver` — нужно пересобрать образ):
```
docker compose up -d --build
```

Остановить всё (данные в volume'ах сохранятся):
```
docker compose down
```

Остановить и УДАЛИТЬ все данные (базу, медиа, redis) — только если
осознанно хочешь начать с чистого листа:
```
docker compose down -v
```

## Деплой на реальный сервер

1. Купи VPS (DigitalOcean, Timeweb, Selectel — любой с Ubuntu 22.04+,
   для старта хватит 2 CPU / 4 GB RAM).
2. Установи на нём Docker так же, как в шаге 1 выше (для Linux —
   `curl -fsSL https://get.docker.com | sh`).
3. Склонируй репозиторий на сервер, настрой `.env` как в шаге 2 (домен
   в `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` — уже реальный, например
   `dopx.kz`), `DEBUG=False`.
4. Направь A-запись домена на IP сервера (в панели регистратора
   домена).
5. Папки `media/` и `logs/` смонтированы в контейнеры напрямую (bind
   mount, см. `docker-compose.yml`), а не через Docker volume — на
   голом Linux-сервере (в отличие от Docker Desktop на Mac) права
   проверяются по-настоящему, и без этого шага Django получит "Permission
   denied" при первой же попытке сохранить аватарку или лог. Один раз
   перед первым запуском:
   ```
   mkdir -p media logs
   sudo chown -R 1000:1000 media logs
   ```
   (1000 — фиксированный UID пользователя `django` внутри контейнера,
   см. `Dockerfile`.)
6. `docker compose up -d --build`.
7. На этом этапе сайт уже доступен по `http://твой-домен` — но без
   HTTPS. Дальше — SSL.

### Настройка HTTPS (Let's Encrypt, бесплатно)

Проще всего — через certbot в отдельном разовом контейнере:

```
mkdir -p docker/certbot/conf docker/certbot/www

docker run --rm \
  -v "$(pwd)/docker/certbot/conf:/etc/letsencrypt" \
  -v "$(pwd)/docker/certbot/www:/var/www/certbot" \
  -p 80:80 \
  certbot/certbot certonly --standalone \
  -d dopx.kz -d www.dopx.kz \
  --email admin@dopx.kz --agree-tos --no-eff-email
```

(Перед этим на минуту останови docker-compose, чтобы порт 80 был
свободен: `docker compose stop nginx`.)

После получения сертификата в `docker/certbot/conf/live/dopx.kz/`
появятся `fullchain.pem` и `privkey.pem`. Дальше:

1. В `docker-compose.yml` раскомментируй порт `443` и монтирование
   `docker/certbot/conf`/`docker/certbot/www` в сервисе `nginx`.
2. В `docker/nginx.conf` раскомментируй весь HTTPS-блок внизу файла и
   замени верхний HTTP-блок на редирект (шаблон там же, в комментарии).
3. `docker compose up -d --build`.

Сертификат Let's Encrypt живёт 90 дней — продление нужно будет
автоматизировать через cron на сервере (задача на будущее, когда дойдут
руки; сейчас — ручное продление той же командой certbot раз в 2–3 месяца).

## Бэкапы базы данных

Ручной бэкап:
```
docker compose exec db pg_dump -U <DB_USER> <DB_NAME> > backup_$(date +%Y%m%d).sql
```

Восстановление из бэкапа:
```
cat backup_20260101.sql | docker compose exec -T db psql -U <DB_USER> <DB_NAME>
```

Рекомендация: настроить это по cron на сервере раз в сутки с ротацией
старых файлов и загрузкой в отдельное хранилище (S3-совместимое, Yandex
Object Storage и т.п.) — это отдельная задача, не входит в этот стек "из
коробки".

## Деплой с aaPanel

aaPanel — панель управления сервером с собственным веб-сервером (Nginx/
Apache/OpenLiteSpeed) и своим Docker-модулем. Ключевое, что нужно понять:
**aaPanel ставит СВОЙ nginx прямо на ОС, вне Docker, и он занимает порты
80/443 сам**. Если наш docker-compose тоже попробует повесить СВОЙ nginx-
контейнер на 80/443 — они столкнутся, второй просто не запустится
("address already in use"). Поэтому схема отличается от "голого" VPS:

```
Интернет → aaPanel-nginx (80/443, свой SSL) → наш nginx-контейнер (127.0.0.1:8080) → gunicorn
```

aaPanel остаётся "фасадом": держит домен, сертификат, редирект на HTTPS.
Наш docker-compose стек как был, так и остаётся — просто его nginx
теперь смотрит не в интернet напрямую, а только на сам сервер.
В `docker-compose.yml` и `.env.example` это уже настроено под эту схему
(порт nginx — `127.0.0.1:8080:80`, `TRUSTED_PROXY_COUNT=2` — см. комментарии
в обоих файлах).

### Пошагово

1. **Установи aaPanel** (по инструкции с aapanel.com — однострочный
   install-скрипт для Ubuntu/CentOS/Debian). При первой настройке она
   предложит поставить веб-стек — выбери **Nginx** (LNMP), он нужен: без
   него не будет одной кнопки "Reverse Proxy", про которую ниже.

2. **Поставь Docker через App Store aaPanel** (вкладка "App Store" →
   найти "Docker" → установить) — либо тем же способом, что в разделе
   выше (`curl -fsSL https://get.docker.com | sh`), работает и так, и
   так, это один и тот же Docker.

3. Открой в файрволе (и в security group у хостера, если облако) порты
   `80`, `443`, `22` (SSH) и `31750` (панель aaPanel, у себя дальше
   можно сменить). Порт `8080` открывать НЕ нужно — он на `127.0.0.1`,
   снаружи и так недоступен.

4. Склонируй репозиторий на сервер, настрой `.env` как в разделе выше
   (шаги 2–5 "Деплой на реальный сервер"): `DEBUG=False`, реальный
   `SECRET_KEY`, домен в `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS`, VAPID-
   ключи, `chown -R 1000:1000 media logs`. Плюс отдельно для этой схемы:
   ```
   TRUSTED_PROXY_COUNT=2
   ```
   (два прокси подряд перед gunicorn — aaPanel-nginx и наш nginx-контейнер;
   если оставить 1, `core.utils.get_client_ip` начнёт возвращать не IP
   посетителя, а внутренний адрес нашего nginx-контейнера — сломается
   rate-limit на регистрации/логине и антифрод-логи будут врать).

5. `docker compose up -d --build`. Проверь, что стек поднялся и отвечает
   изнутри сервера: `curl -I http://127.0.0.1:8080` — должен вернуть
   заголовки, а не "connection refused".

6. В aaPanel: **Website → Add site**, укажи домен (`dopx.kz`), PHP-версию
   не выбирай/оставь "Pure static" (она тут не используется, весь запрос
   уйдёт в проксю).

7. Открой созданный сайт → **Reverse Proxy** (или "Proxy Project" в
   некоторых версиях панели) → добавить прокси, целевой адрес
   `http://127.0.0.1:8080`, включить.

8. Там же в сайте → **SSL** → выбрать **Let's Encrypt** → Apply. Панель
   сама выпустит сертификат и продлит его позже без твоего участия.
   Включи опцию принудительного редиректа на HTTPS.

9. Открой `https://твой-домен` — сайт должен открыться уже с сертификатом.
   Ручной certbot из раздела про HTTPS выше в этой схеме не нужен —
   aaPanel сам всё закрывает.

### Если решишь отказаться от aaPanel-панели для этого домена

Тоже вариант — тогда наш nginx-контейнер может забрать 80/443 себе
напрямую (верни `"80:80"`/`"443:443"` в `docker-compose.yml` вместо
`127.0.0.1:8080:80`, `TRUSTED_PROXY_COUNT` верни на `1`), и HTTPS настраивать
через certbot как в разделе "Настройка HTTPS" выше. Но тогда aaPanel'овский
Website/SSL-раздел для этого домена лучше не трогать вообще, чтобы не
было двух web-серверов, спорящих за один порт.

## Автодеплой: push в main → сервер сам обновляется

Это то, что у знакомого — пушишь в GitHub, сервер сам подтягивает код,
пересобирает и перезапускает контейнеры. Реализовано через GitHub
Actions: `.github/workflows/deploy.yml` уже лежит в репозитории и
работает в два шага при каждом push:

1. **build-check** — на любой push в `main`/`dev` собирает Docker-образ
   (`docker build`), ничего не разворачивая. Это ловит именно те ошибки,
   которые мы недавно чинили руками (несовпадение версии Python,
   несуществующая версия пакета) — до того, как они попадут на сервер.
2. **deploy** — только на push в `main`, и только если build-check прошёл:
   заходит на сервер по SSH и выполняет `git pull` + `docker compose up
   -d --build`.

Пока сервера нет, шаг deploy сам себя пропускает с сообщением в логах —
это нормально, не ошибка. Сборка (build-check) при этом уже проверяется
на каждый push, так что часть пользы работает прямо сейчас.

### Что сделать один раз, когда появится сервер

1. Выполни шаги "Деплой на реальный сервер" выше (Docker на сервере,
   `.env`, домен) — сайт должен подниматься вручную через `docker compose
   up -d --build`, прежде чем автоматизировать.

2. На сервере убедись, что он сам может делать `git pull` из GitHub.
   Проще всего — Deploy Key (в GitHub: репозиторий → Settings → Deploy
   keys → Add deploy key, ключ read-only, этого достаточно):
   ```
   ssh-keygen -t ed25519 -f ~/.ssh/dopx_readonly -N ""
   cat ~/.ssh/dopx_readonly.pub   # это вставить в Deploy keys на GitHub
   ```
   и в `~/.ssh/config` на сервере указать использовать этот ключ для
   `github.com`, либо просто клонировать репозиторий по этому ключу.

3. Сделай отдельный SSH-ключ для самого GitHub Actions (это ключ, которым
   *Actions заходит на сервер*, отличается от ключа из шага 2, которым
   *сервер заходит на GitHub*):
   ```
   ssh-keygen -t ed25519 -f ~/.ssh/dopx_deploy -N ""
   ```
   Публичную часть (`dopx_deploy.pub`) добавь на сервере в
   `~/.ssh/authorized_keys` пользователя, под которым будет заходить
   Actions. Приватную часть (`dopx_deploy`, без `.pub`) — в GitHub
   Secrets на следующем шаге.

4. В репозитории на GitHub: Settings → Secrets and variables → Actions →
   New repository secret. Добавь четыре секрета:
   - `DEPLOY_HOST` — IP или домен сервера.
   - `DEPLOY_USER` — SSH-пользователь на сервере.
   - `DEPLOY_SSH_KEY` — содержимое приватного ключа `dopx_deploy` целиком
     (включая строки `-----BEGIN...`/`-----END...`).
   - `DEPLOY_PATH` — абсолютный путь к проекту на сервере, например
     `/home/deploy/dopx`.

   Всё, больше ничего не трогать — `.github/workflows/deploy.yml` уже
   готов их подхватить.

5. Проверка: сделай любой пуш в `main` (например, смёрджи PR из `dev`) и
   открой вкладку Actions в репозитории на GitHub — увидишь, как
   отрабатывают build-check и deploy.

Секреты (`.env` на сервере) через этот механизм не трогаются и не
пересылаются — они как были только на сервере, так и остаются, деплой их
не видит и не должен.

## Чек-лист перед реальным продакшном

Обязательно перед тем, как пускать реальных пользователей:

- `DEBUG=False` в `.env`.
- `SECRET_KEY` — случайная строка, не значение по умолчанию из кода.
- `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS` — реальный домен, не `*`.
- HTTPS настроен (см. выше), `SECURE_SSL_REDIRECT=True`.
- Пароль от Postgres (`DB_PASSWORD`) — не дефолтный/не короткий.
- Настроен email (`EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`) — иначе не
  уйдут письма подтверждения регистрации, сброса пароля, дайджестов.
- `SENTRY_DSN` заполнен — иначе об ошибках на проде узнаешь только от
  пользователей в комментариях.
- VAPID-ключи (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`) заполнены В `.env`
  ДО первого запуска на сервере, и `VAPID_PRIVATE_KEY` — это СОДЕРЖИМОЕ
  ключа (короткая строка), а не путь к .pem-файлу (см. `.env.example`,
  там же команда конвертации, если ключ уже есть как файл). Если оставить
  их пустыми, `core/services/vapid.py` сам сгенерирует пару при первом
  `migrate` — но в Docker это исполнится ВНУТРИ контейнера и допишется в
  файл `.env` внутри контейнера, а не в реальный `.env` на сервере,
  который читает `docker-compose.yml`. При следующем пересоздании
  контейнера (`docker compose up -d --build`) сгенерируется НОВАЯ пара
  ключей — все, кто успел подписаться на push, молча перестанут получать
  уведомления. Поэтому: сгенерировать один раз ДО деплоя (локально —
  `python manage.py setup_push_keys`, или просто взять готовую пару из
  локального `.env`) и вписать в серверный `.env` вручную.
- Бэкапы БД настроены (см. выше) — без них потеря сервера = потеря всех
  данных.
- Firewall на сервере пропускает только 80/443/22 (SSH) — сами
  контейнеры db/redis/web порты наружу не публикуют (см.
  `docker-compose.yml`, у них нет `ports:`), но лишним не будет закрыть
  и уровень ОС.
